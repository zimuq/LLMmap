---

## Why this D, in one paragraph

Three recent papers report MET and ZeroPrint, and their rankings disagree
wildly. MET is near the bottom in AdaptPrint (Top-1 4–8%) but the best
black-box baseline in BReF (Top-1 64%); ZeroPrint is the reverse (48–78% vs
32%). The literature report reads this as two opposite failure modes:
- MET compares raw characters, so it is sensitive to *any* distribution
  shift — good for near-relatives, bad under deployment-config shift;
- ZeroPrint is built to be invariant to derivation — good under config
  shift, bad for near-relatives.

Our task has both difficulties. Numbers from other papers do not transfer, so
we reproduce both methods **under their native protocols, in our setting**.

---

## D — The question

> **On corpus v2's 85 models (and the 37-model v1 subset), with a target
> deployed under an unknown S_test config, how well do MET and ZeroPrint
> identify the model when run under their own native protocols? And how do
> they compare to our method (JointGreedy `k` = 8 + trained readout) and to
> PAPER8, on the same models and the same test configs?**

### Three reference / target settings per method (AdaptPrint's Gen/All idea, plus a no-shift row)

| row | reference library (per model) | target (per model) | what it measures |
|---|---|---|---|
| **native** | native config | native config, independent samples | the method's own setting, no config shift. Descriptive ceiling only: our method never gets this luxury |
| **Gen** | native config | each S_test config | reference covers one config |
| **All** | each sample slot under one config drawn uniformly from that model's 75 S_build configs (I2) | each S_test config | reference covers deployment configs (the D024 idea) |

### Representation variants, computed post hoc on the same generations (no extra generation)

| method | primary (original paper) | variant |
|---|---|---|
| **MET** | **MET-Hamming**: prompt-aware normalised Hamming kernel on Unicode characters, L = 1000, unbiased MMD | **MET-e5**: same prompt-aware unbiased MMD, completions embedded with the frozen I5 model (D028 embedding settings), RBF kernel with bandwidth = median pairwise distance over the Gen reference pool (all 85 models' Gen samples; fixed before any target is scored) |
| **ZeroPrint** | **ZP-512**: official code, outputs as generated (≤ 512 tokens) | **ZP-200**: each output truncated to its first 200 tokens (generating model's tokenizer; our corpus cap) before embedding. Valid because `max_new_tokens` is a stopping rule (D006) |

Note: ZeroPrint's own embedder (all-mpnet-base-v2) and MET's character kernel
are each method's native representation, so they are **not** I5
substitutions. I5 governs our pipeline.

### Identification rule (BReF's convention, the method's native score)

- MET: predict argmin over candidates of MMD(target sample, reference_m).
- ZeroPrint: predict argmax of Pearson(target fingerprint, reference_m).
- **Ties are pre-registered:**
  - top-1 gets fractional credit 1/|tie set| if the true model is in the
    tie set;
  - a pairwise comparison that ties scores 0.5;
  - R reports the tie rate. AdaptPrint attributed MET's collapse to ties.
- No permutation p-values. Identification is a ranking, not a test.

### Comparators (no new runs; existing counts, same test configs)

| corpus view | ours | PAPER8 |
|---|---|---|
| **v2, 85-way** | D029 JG, `k` = 8, attention (seeds 0–4) and linear | D029 PAPER8, `k` = 8 |
| **v1, 37-way** | D010 JG `k` = 8 (attention) / D020 (linear), on corpus v1 | D009 / D020 PAPER8 |

- **v1 rule (D029 "two corpora", rule 1):** our v1 numbers stay on corpus v1
  and are not retrained on v2 data. Baselines on the v1 view are their own
  generations, restricted to the 37 v1 models (37-way candidate set).
- The only mismatch is that the 3 gemma models' baseline generations come
  from the v2 environment (human, 2026-10-08). Same configs, different
  serving environment; disclose it.
- **Pairing:** S_test configs are per model, and the 25 slots are shared
  with the comparators' `cnt_model` arrays (85 × 25 / 37 × 25). Baselines must
  be generated on exactly those slots.

### Descriptive extra (no generation): LLMmap as others run it

- **LLMMAP-OS:** LLMmap's released pretrained open-set encoder on PAPER8
  traces from the frozen corpus (v1 view on corpus v1, v2 view on corpus v2).
  Responses truncated to 650 characters, as in the released code.
  - Reference Gen = the D024 SINGLE config (tier 1, greedy).
  - Reference All = mean fingerprint over the 75 S_build configs.
  - Prediction by cosine distance.
- **Why:** ZeroPrint and BReF both report LLMmap this way, so readers will
  compare against this mode. Our PAPER8 is the closed-set retrained mode.
- If the released encoder cannot be loaded, report that and skip this row;
  it is not a stop condition.

## Native protocols (fixed here; P may not change them)

| | **MET** (official repo, commit fixed in P) | **ZeroPrint** (official repo `shaoshuo-ss/ZeroPrint`, commit fixed in P; BReF used `16a02aa`) |
|---|---|---|
| prompts | 25 multilingual Wikipedia prompts from MET's released prompt distribution, drawn **once** (seeded) and shared by all 85 models | HumanEval reservoir per official code: first 20 words, prefix "Complete the following code:", ≥ 15 words; **2** base queries × (1 + **4** GloVe perturbations, glove-wiki-gigaword-100, 3 words replaced from the top-10 neighbours) = **10** prompts, drawn **once** (seeded) and shared |
| samples per prompt | 10 | 20 |
| decoding, native config | chat template, no system message, T = 1.0, top-p = 1.0, no top-k | chat template, no system message, T = 0.7, top-p = 0.9, top-k = 50 |
| decoding under our configs | the config's own system prompt / RAG / CoT wrapper and sampling settings (the deployment) | same |
| max new tokens | 50 (native, in every setting) | 512 (native, in every setting) |
| stored | full raw text, plus token counts and finish reason | same |

- **Wrapping:** under a config, the baseline prompt takes the place of the
  pool query, wrapped by the config exactly as corpus v2 generation wraps it
  (`d027_llm.py`, each model's D027/D028 environment, as in D028's
  multilingual extension).
- **No-system-message native config** is a deployment mode that exists in
  every pool (A7 carve-out), so it is not a split leak.

### Generation volume per model

| | Gen ref | All ref | native target | S_test targets | total |
|---|---|---|---|---|---|
| MET | 250 | 250 | 250 | 250 × **25** (all slots) | **7,000** |
| ZeroPrint | 200 | 200 | 200 | 200 × **T_ZP** | 600 + 200·T_ZP |

- **85 models:**
  - MET: 595,000 generations, ≤ 50 tokens each;
  - ZeroPrint: 136,000 at T_ZP = 5, 476,000 at T_ZP = 25, ≤ 512 tokens each.
- **T_ZP is not fixed here.** S0 measures cost, and the human picks T_ZP
  from {5, 10, 25} (Call).
- **The T_ZP subset rule is fixed now.** For each model:
  1. group its 25 S_test slots by config type (none / system prompt / RAG /
     CoT, as recorded in `prompt_conf`);
  2. sort each group by slot index;
  3. take slots round-robin across the groups until T_ZP are taken.

  This uses config metadata only. P lists the chosen slots before any
  generation.
- **MET's T_ZP-slot subset** is reported alongside, so all three methods
  can be compared on identical configs.
- **Design-side cost guess**, to be replaced by S0's measurement: MET ≈ 15–20
  node-h; ZeroPrint ≈ 40 node-h at T_ZP = 5. Corpus v2's generation took
  192 node-h for 1.65M × ≤ 200 tokens.

## What counts as an answer

**Endpoints** (S_test targets, read once; per corpus view):
- **E_all:** mean top-1 over all models × test slots. 85-way (v2) / 37-way
  (v1).
- **E_hard:**
  - v2: mean two-logit accuracy over H_all (57 pairs, D029 definition).
  - v1: CVaR₀.₁ of two-logit accuracy over the 666 pairs (D016 / D024
    convention).
  - For baselines, a pairwise "logit" is the native score of the two
    candidates.
- **Literature-comparable (descriptive):** Top-3, MRR. Also exact McNemar
  on per-trace top-1 (linear readout vs each baseline), Holm-corrected,
  following BReF.

**Strongest-baseline rule** (D024 lesson, pre-registered):
- For each method, B* = the variant with the highest E_all point estimate
  among {Gen, All} × {primary, representation variant}, per corpus view.
- The native row is excluded from B*: it is not our task.
- The verdict is against B*. Every variant is reported.

**Primary contrast:** Δ = OURS(JG `k` = 8, attention) − B*, on both E_all and
E_hard.
- Interval: D023's hierarchical config × seed bootstrap (2,000 draws; one
  draw set shared by every arm). Baselines have no seed dimension, so only
  their configs are resampled.
- ZeroPrint comparisons use the T_ZP slots only.

| label (per method × corpus view) | rule |
|---|---|
| **BETTER** | lo(Δ_all) > 0 **and** lo(Δ_hard) > 0, **and** linear Δ agrees in sign on both |
| **PARITY** | both intervals ⊂ [−0.02, +0.02] |
| **WORSE** *(headline)* | hi(Δ_all) < 0 **or** hi(Δ_hard) < 0 |
| **INCONCLUSIVE** | otherwise |

- The v2 view is primary for the paper. The v1 view uses the same rule and
  is reported with equal prominence (the human wants both). The two are
  never compared as levels (D029 rule 2).
- **A WORSE in any cell** goes first in R and in the Review's "For you".

**The opposite-failure hypothesis** (descriptive, stated before any data):
- MET's loss relative to ours will be concentrated in the config-shift rows:
  Gen/All ≪ native.
- ZeroPrint's loss will be concentrated on near-relative pairs: E_hard ≪
  E_all relative to ours, and worst on the structural pairs (N′ / N).
- R reports native − Gen, native − All, and the H_all / structural
  breakdown for each method. Nothing here is a verdict.

**Secondary (descriptive):**
- (a) MET-Hamming vs MET-e5, and ZP-512 vs ZP-200, as paired differences.
  These say how much representation and truncation matter.
- (b) E_all by block: v2 new 48 vs v1 37 (D029 blocks).
- (c) Each method's E_all by config type (none / system prompt / RAG / CoT)
  on the S_test slots.
- (d) LLMMAP-OS rows (Gen, All), both views.
- (e) Mandatory hard-tail plot (CLAUDE.md): two-logit accuracy over all pairs
  per method at the primary setting, both views.

## Multi-P structure — first trial of this format (human, 2026-10-09)

Every earlier D had a single P1. This D deliberately has several. The rules
below apply to this D only; they will be condensed into `CLAUDE.md` if the
trial works.

**Mandatory review stops (design-side fixed; TACC may not merge across them):**

| stop | when | why |
|---|---|---|
| **A** | after the S0 freeze + pilot, **before any full generation** | the generation is expensive and irreversible (I7); the human picks T_ZP here |
| **B** | after S1 generation + its health report, **before any S_test score is computed** | the last point at which evaluation rules (kernel bandwidth, tie rule, variants) can change at no cost |

**Splitting is TACC's call.**
- The minimum is **P1 = S0 + S1** (with stop A inside it, see below) and
  **P2 = S2 + S3 + S4**.
- TACC may split further (e.g. P2 = scoring, P3 = analysis) where execution
  granularity makes that sensible. P1 states the intended split.
- It must never place stop A or B inside one approved P without a review in
  between.
- Stop A sits *inside* P1. P1 is approved for S0 only; S1 proceeds after an
  appended `## Review` note (P1 / stop A) approves T_ZP and the total. No
  new P is needed for that, unless S0 changes the plan.

**Mechanics:**
- **Each P{n}:**
  - has its own plan file `docs/plans/D030-P{n}.md`;
  - gets its own summary under `## P`, headed "P{n}";
  - gets its own `## Review` (P{n}).
- **P{n+1} is written only after R-P{n} is posted.** It may use P{n}'s actual
  outputs (e.g. generation health), and states what it took from them.
- **Results are per P:** R-P1, R-P2, … under `## R`. The last P adds an
  **R-final** that gives the labels first and points to the per-P sections.
- **PLAN.md status names the stage**, e.g. "P1 APPROVED (S0 only) —
  executing", "stop A — awaiting T_ZP", "P2 not yet written".
- **The code-change rule** (`CLAUDE.md`) applies to whichever P is awaiting
  review.
- **If a later P must change something an earlier, approved P fixed** (a
  prompt, a seed, a manifest field), that is a Call in the new P. The earlier
  P is never edited after approval.

**Process feedback.** In R-final, TACC adds a short note on whether the
multi-P format helped or hindered, and what should change before it is
written into `CLAUDE.md`.

## Review — D030 / P1 (S0 only)

### For you (human)

**Verdict:** APPROVED WITH AMENDMENTS — S0 only, i.e. freezing, checks and
the cost pilot. Full generation still waits for stop A.

**What changed**
- **ZeroPrint's 5–10 test configs are reordered.** The proposed order would
  have taken the "no system prompt" configs first, and twice at 5 slots.
  That is the easiest case and the rarest one (7%). The new order starts
  with the most common type, system prompts (65%).
- **The purge-guard job is dropped unless TACC's policy allows it.** It
  would read every weight file only to stop the 10-day scratch purge. TACC
