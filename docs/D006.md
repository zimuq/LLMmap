## D — The question

> **Can the real Phase-1 corpus — the 37-model ≤14B universe, the final
> query pool `Q_0`, and build/val/test traces for every model — be
> generated within Vista's actual operating constraints (2-day per-job
> cap, `$SCRATCH`'s 10-day purge window, SU balance), while satisfying
> invariants I1, I2, I3, I5, I7, and land as one frozen, versioned
> artifact ready for tensor construction?**

**This is not the corpus D001/D004/D005 analyzed.** Those reused LLMmap's
already-shipped corpus (for premise-testing, embedded with LLMmap's own
384-d classifier, cached at `results/D001/f_test.npy`). D006 builds this
project's *own* corpus from scratch, embedded with the frozen I5 model
(`multilingual-e5-large-instruct`, 1024-d). Nothing here touches or
depends on the earlier one.

### Why this D exists now, and why it stops where it does

Everything this D needs is now in place: **A1** (37 models, decided
2026-09-05 — see exact list below), **C3/D003** (233-entry candidate
query pool, `confs/queries/pool_d003_candidates.json`), **C4** (75/25/25
split sizes, decided 2026-09-05), **D005** (I2 actually holds now, with
the A5 `do_sample` carve-out documented). D002 established GPU is
available and SUs are not the binding constraint; what binds is wall-clock
against the `$SCRATCH` purge window and — new, from TACC's 2026-09-04
report — Vista's `gh` partition capping any single job at **2 days**,
which makes per-model sharded, parallel execution **mandatory**, not an
optimization.

This D corresponds to TODO.md's **T1.1–T1.4** (fix universe, build `Q_0`,
construct the split, collect the corpus). It deliberately **stops before
T1.5/T1.6** (build the actual separability tensor; run the mandatory
hard-tail check) — both are blocked on **A3** (which two-sample

Don't let tensor-construction questions creep into this D's scope.

## What counts as an answer

| Outcome | Criterion |
|---|---|
| **READY** | Every one of the 37 models has a complete, validated shard (all build/val/test configs, all `Q_0` queries); the corpus is embedded with I5; a single manifest (schema version, model list, generation date, per-model shard status) exists; I1/I2/I3/I7 verified to hold on the assembled result. |
| **PARTIAL** | One or more models' shards are incomplete or failed after retry. Report which, why, and whether the D can still be usefully closed with a documented gap (e.g. a model genuinely unobtainable) or needs another pass. |
| **BLOCKED** | A platform or invariant obstacle this D did not anticipate prevents completion (e.g. a model that won't load on aarch64, a cost overrun past the guardrail below). Stop and report — do not work around it silently. |

## Required steps

**S1 — Fix `dataset_maker.py`'s batch-1 generation loop (D002 §R4).** This
is the mandatory prerequisite D002 identified and explicitly deferred to
"the Phase-1 D" — this is that D. Use the batching support
`LLM_huggingface.generate` already has (`llm.py:74-89`). **Verify
numerically that batched output matches unbatched** (same response
distribution, not just "runs without error") before relying on it for the
real corpus — mirroring D002's own CPU-vs-GPU cross-check discipline.
Nontrivial change to a shared module: disclose the exact diff in P per the
code-change rule, same standard as D002's environment changes and D005's
`prompt_configuration.py` fix.

**S2 — Assemble the final `Q_0`.** Combine:
- D003's 233-entry candidate pool as-is.
- **Tokenizer-level probes** (TODO.md's own phrasing, extracted here since
  TACC doesn't see TODO.md directly): four categories — *digit chunking*,
  *whitespace merging*, *rare-Unicode byte fallback*, *glitch tokens*.
  These don't exist in any form yet. **Call 1** (design-side review
  required before finalizing, same posture as D003's Call 1/Call 2):
  propose ~5–10 concrete instances per category in P. The paper itself
  flags glitch tokens as unexplored (§5.1) — there's no existing baseline
  to match; this is genuinely new construction, not transcription.
- Tag every entry's provenance the same way D003 did (`anchor` /
  `generated-<family>` / **new:** `tokenizer-probe-<category>`).
- Report final size and per-category/family counts in `## R`.

**S3 — Construct `S_build` / `S_val` / `S_test`.** Per C4 (75/25/25,
decided), using D005's now-fixed `PromptConfFactory` (I2 holds; `do_sample`
shared per the A5 carve-out). Reuse D005's own disjointness test
(`experiments/test_i2_disjointness.py`) against the splits actually
produced here — don't re-derive a new check, confirm the existing one
passes on this D's output.

**S4 — Shard generation by model, one job per model.** Per TACC's
2026-09-04 report: Vista's `gh` partition caps any single job at 2 days,
so single-node/single-job execution isn't viable at this scale regardless
of preference — sharding is mandatory. Up to 20 concurrent jobs
(`MaxJobsPU=20`); each shard independently restartable, writes its own
output; one model's failure doesn't block the rest. For each model: run
every `Q_0` query under **every one of its build/val/test configs (all
125, not just the 75 `S_build` configs)** — see note below.

> **Why generate under all 125 configs now, not just the 75 `S_build`
> configs TODO.md's own T1.4 arithmetic assumed:** T1.5/T1.6 (tensor
> construction, hard-tail check) only need `S_build`, but later phases
> (T3.3, T4.2) need `S_val`/`S_test` traces too. Loading each model once
> and generating under everything needed in this one pass avoids
> re-loading every model again later purely to collect the remaining
> splits — a real efficiency argument, not scope creep. This does **not**
> conflict with I2's discipline or T4.2's "`S_test` touched once" rule:
> that rule is about *analysis* (not looking at test results until Phase
> 4), not about *when the raw data is collected*. Decided here as a
> routine implementation-efficiency call — flag in P if this reasoning
> doesn't hold for some reason not anticipated here.

**S5 — Reassembly design (flagged by TACC as needing design-side input,
not to be decided unilaterally).** Propose in P, **Call 2**:
- A manifest format: schema version tag (I7 — this is the first version
  of this project's own corpus; state the tag explicitly even with no
  prior version to migrate from), model list, generation date, per-model
  shard completeness/checksum.
- An explicit **freeze point**: the corpus is not "the frozen corpus" (I6)
  until every shard is validated complete — define "validated" (e.g. row
  counts match `|Q_0| × 125` per model, no truncated/malformed entries) so
  there's no ambiguous half-done state something downstream could
  mistake for final.
- A position on partial failure: is a corpus with, say, 35/37 models
  complete usable as an interim state, or must all 37 land before
  anything downstream touches it? State one; affects whether S4's
  per-model retries can happen out of band from a "ready" declaration.

**S6 — Embed every response with the frozen I5 model**
(`multilingual-e5-large-instruct`, 1024-d) — the actual raw material for
the eventual separability tensor, and explicitly **not** the same
representation D001/D004 used. Store full point clouds (every response's
embedding, not a collapsed average) — I3 requires point-cloud-vs-point-
cloud comparison downstream, which can't be reconstructed later if only
summary statistics are kept now.

**S7 — Verify invariants hold before declaring READY:**
- I1: trivially satisfied (65 near-relative pairs across the 37 —
  already established, D001).
- I2: rerun D005's disjointness test against this D's actual *generated*
  splits (not just the split *definition* files — confirm the generated
  data respects them, not only that the definitions do).
- I3: confirm storage format preserves full point clouds, not collapsed
  vectors.
- I7: confirm the manifest states an explicit schema version.

**S8 — Write `## R`:** final `Q_0` composition (with tokenizer-probe
counts), per-model shard status, actual total generations/cost/wall-clock
(compare against the guardrail below), corpus manifest location, and
I1/I2/I3/I7 verification results.

## Constraints

**Applicable invariants:** I1, I2, I3, I5, I7 all bind directly (this is
the real corpus, not a pilot). I6 applies going forward from the moment
this D declares the corpus frozen. I4 doesn't bind on construction itself
(it governs how coverage is computed *from* the tensor — the next D's
concern) but the storage format (S6) must not foreclose it.

**Code-change rule applies in full to S1** (the `dataset_maker.py`
batching fix) — disclose the exact diff in P before executing, don't fold
it in silently, same standard as D002's environment changes and D005's
`prompt_configuration.py` fix.

**Out of scope:** building the actual `Sep(·,·)` tensor, running
`GreedyCover`, any mean-vs-CVaR comparison, the mandatory hard-tail check
(TODO.md T1.6). All blocked on A3 (still open) and belong to a follow-on D
once A3 resolves.

**Budget guardrail.** Per TACC's 2026-09-04 estimate, scaled to 37 models:
~126–218 node-hours (37 × 233 × 125 generations, batch-8, 100–200 tok),
~1.8–3.1% of the 6982 SU balance, ~4–6 hours wall-clock across ~2 waves of
≤20 concurrent jobs. If actual costs run meaningfully past this — not a
rounding difference, a different order of magnitude — **stop and report
rather than continuing to spend past it silently**, per the code-change
rule's disclosure spirit.

**`$SCRATCH` purge window applies as established (D002 §P1.a):** weights
on `$SCRATCH` (re-downloadable, no quota, purged after 10 days of no
compute-node access); corpus/results on `$WORK` (no purge). At ~4–6 hours
wall-clock this D is nowhere near the purge window, but state explicitly
in P where each artifact lands.
