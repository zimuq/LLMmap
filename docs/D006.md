## Required steps

**S1 — Fix `dataset_maker.py`'s batch-1 generation loop (D002 §R4).** This
is the mandatory prerequisite D002 identified and explicitly deferred to
"the Phase-1 D" — this is that D. Use the batching support
`LLM_huggingface.generate` already has (`llm.py:74-89`). **Verify
numerically that batched output matches unbatched** (same response
distribution, not just "runs without error") before relying on it for the
real corpus — mirroring D002's own CPU-vs-GPU cross-check discipline.
Nontrivial change to a shared module: disclose the exact diff in P per the
code-change rule, same standard as D002's environment changes and D005's
`prompt_configuration.py` fix.

**S2 — Assemble the final `Q_0`.** Combine:
- D003's 233-entry candidate pool as-is.
- **Tokenizer-level probes** (TODO.md's own phrasing, extracted here since
  TACC doesn't see TODO.md directly): four categories — *digit chunking*,
  *whitespace merging*, *rare-Unicode byte fallback*, *glitch tokens*.
  These don't exist in any form yet. **Call 1** (design-side review
  required before finalizing, same posture as D003's Call 1/Call 2):
  propose ~5–10 concrete instances per category in P. The paper itself
  flags glitch tokens as unexplored (§5.1) — there's no existing baseline
  to match; this is genuinely new construction, not transcription.
- Tag every entry's provenance the same way D003 did (`anchor` /
  `generated-<family>` / **new:** `tokenizer-probe-<category>`).
- Report final size and per-category/family counts in `## R`.

**S3 — Construct `S_build` / `S_val` / `S_test`.** Per C4 (75/25/25,
decided), using D005's now-fixed `PromptConfFactory` (I2 holds; `do_sample`
shared per the A5 carve-out). Reuse D005's own disjointness test
(`experiments/test_i2_disjointness.py`) against the splits actually
produced here — don't re-derive a new check, confirm the existing one
passes on this D's output.

**S4 — Shard generation by model, one job per model.** Per TACC's
2026-09-04 report: Vista's `gh` partition caps any single job at 2 days,
so single-node/single-job execution isn't viable at this scale regardless
of preference — sharding is mandatory. Up to 20 concurrent jobs
(`MaxJobsPU=20`); each shard independently restartable, writes its own
output; one model's failure doesn't block the rest. For each model: run
every `Q_0` query under **every one of its build/val/test configs (all
125, not just the 75 `S_build` configs)** — see note below.

> **Why generate under all 125 configs now, not just the 75 `S_build`
> configs TODO.md's own T1.4 arithmetic assumed:** T1.5/T1.6 (tensor
> construction, hard-tail check) only need `S_build`, but later phases
> (T3.3, T4.2) need `S_val`/`S_test` traces too. Loading each model once
> and generating under everything needed in this one pass avoids
> re-loading every model again later purely to collect the remaining
> splits — a real efficiency argument, not scope creep. This does **not**
> conflict with I2's discipline or T4.2's "`S_test` touched once" rule:
> that rule is about *analysis* (not looking at test results until Phase
> 4), not about *when the raw data is collected*. Decided here as a
> routine implementation-efficiency call — flag in P if this reasoning
> doesn't hold for some reason not anticipated here.

**S5 — Reassembly design (flagged by TACC as needing design-side input,
not to be decided unilaterally).** Propose in P, **Call 2**:
- A manifest format: schema version tag (I7 — this is the first version
  of this project's own corpus; state the tag explicitly even with no
  prior version to migrate from), model list, generation date, per-model
  shard completeness/checksum.
- An explicit **freeze point**: the corpus is not "the frozen corpus" (I6)
  until every shard is validated complete — define "validated" (e.g. row
  counts match `|Q_0| × 125` per model, no truncated/malformed entries) so
  there's no ambiguous half-done state something downstream could
  mistake for final.
- A position on partial failure: is a corpus with, say, 35/37 models
  complete usable as an interim state, or must all 37 land before
  anything downstream touches it? State one; affects whether S4's
  per-model retries can happen out of band from a "ready" declaration.

**S6 — Embed every response with the frozen I5 model**
(`multilingual-e5-large-instruct`, 1024-d) — the actual raw material for
the eventual separability tensor, and explicitly **not** the same
representation D001/D004 used. Store full point clouds (every response's
embedding, not a collapsed average) — I3 requires point-cloud-vs-point-
cloud comparison downstream, which can't be reconstructed later if only
summary statistics are kept now.

**S7 — Verify invariants hold before declaring READY:**
- I1: trivially satisfied (65 near-relative pairs across the 37 —
  already established, D001).
- I2: rerun D005's disjointness test against this D's actual *generated*
  splits (not just the split *definition* files — confirm the generated
  data respects them, not only that the definitions do).
- I3: confirm storage format preserves full point clouds, not collapsed
  vectors.
- I7: confirm the manifest states an explicit schema version.

**S8 — Write `## R`:** final `Q_0` composition (with tokenizer-probe
counts), per-model shard status, actual total generations/cost/wall-clock
(compare against the guardrail below), corpus manifest location, and
I1/I2/I3/I7 verification results.

## Constraints

**Applicable invariants:** I1, I2, I3, I5, I7 all bind directly (this is
the real corpus, not a pilot). I6 applies going forward from the moment
this D declares the corpus frozen. I4 doesn't bind on construction itself
(it governs how coverage is computed *from* the tensor — the next D's
concern) but the storage format (S6) must not foreclose it.

**Code-change rule applies in full to S1** (the `dataset_maker.py`
batching fix) — disclose the exact diff in P before executing, don't fold
it in silently, same standard as D002's environment changes and D005's
`prompt_configuration.py` fix.

**Out of scope:** building the actual `Sep(·,·)` tensor, running
`GreedyCover`, any mean-vs-CVaR comparison, the mandatory hard-tail check
(TODO.md T1.6). All blocked on A3 (still open) and belong to a follow-on D
once A3 resolves.

**Budget guardrail.** Per TACC's 2026-09-04 estimate, scaled to 37 models:
~126–218 node-hours (37 × 233 × 125 generations, batch-8, 100–200 tok),
~1.8–3.1% of the 6982 SU balance, ~4–6 hours wall-clock across ~2 waves of
≤20 concurrent jobs. If actual costs run meaningfully past this — not a
rounding difference, a different order of magnitude — **stop and report
rather than continuing to spend past it silently**, per the code-change
rule's disclosure spirit.

**`$SCRATCH` purge window applies as established (D002 §P1.a):** weights
on `$SCRATCH` (re-downloadable, no quota, purged after 10 days of no
compute-node access); corpus/results on `$WORK` (no purge). At ~4–6 hours
wall-clock this D is nowhere near the purge window, but state explicitly
in P where each artifact lands.

**Status: PROPOSED — awaiting review.** Full plan:

**D006's anchors verified first, as it asks.** A1's 37-model list: ✅ exact
match against `results/D001/model_metadata.csv`, count and membership, no
discrepancy. I1's 65 near-relative pairs: ✅ sourced to `D001.md:315`, computed
over exactly this subset. Cost 126–218 node-h: ✅ consistent with D002 §R2
(my recomputation: 121–133 at 100 tok, 199–240 at 200 tok). I5 model already
cached on `$SCRATCH`. Storage sized and fine (weights ~478 GB → `$SCRATCH`;
embeddings 4.4 GB fp32 → `$WORK`). SU balance is now 6869, not 6982 —
immaterial.

**Two findings block execution. Neither is resolvable on the TACC side.**

**F1 — `C7` is still open, and D006 would freeze it into the corpus
irreversibly.** D006 mentions C7 nowhere; its only reference to the token
budget is the cost line "100–200 tok", treated as a costing *range*. But S4
must pick one, and it is then baked into all 1,077,625 responses under I6.
`DECISIONS.md` C7 says explicitly *"Decide C7 on information grounds, not
cost — still open"*; D006 would resolve it silently at whatever `llm.py:9`
says (`max_new_tokens = 100`).

This is not hypothetical. Measured on the shipped corpus (62,394 responses):
the share of responses ending mid-sentence is **~4% at 100–299 chars** — the
stylistic baseline — and climbs monotonically to **66.5% (400–499)**, **83.4%
(500–599)**, **91.2% (600–699)**. That is right-censoring at the 100-token
cap: **~38 percentage points of the corpus is truncated.** Signal a 100-token
cap destroys: response length itself, closing/sign-off style, refusal length,
whether an enumerated answer completes.

**This project has already been bitten by exactly this.** D004's finding was
that a statistic on a censored variable measures the censoring, not the
population (M6 = 0.997 censored vs **0.616** uncensored). F1 is that same
hazard moved to the *raw material*, where no later choice of statistic can
undo it — and I7's own stated rationale is that regenerating this corpus is
"the most expensive avoidable mistake here."

**Proposal — make C7 a measurement, not a guess, at ~zero cost.** S1 must
already run real generations to verify batched ≈ unbatched. Extend that same
run to measure censoring at 100 / 200 / 400 tokens on 3 models spanning
0.5B–14B (~1,500 generations, well under an hour, node already loaded).
That gives C7 the "information grounds" it asks for *before* anything
irreversible runs. **My recommendation:** run the pilot; if 200 clears the
ceiling, adopt 200 — 199–240 node-h is 2.9–3.5% of balance and a 10.7–13.0 h
makespan, both far inside the 2-day job cap and the 10-day purge window.
**S1's pilot can run before C7 is decided. S4 cannot.**

**F2 — C4 is a three-way split; the code and configs support two pools.** S3
reads as though the machinery is ready; it is not.
`confs/prompt_configurations/train_test_split.json` has exactly two keys
(`train`, `test`), `prompt_configuration.py:6` defines two constants, and
`_cond_choice` (`:256`) would `KeyError` on a third. D005 fixed a *two*-pool
split. The extension is not mechanical because the collections are thin:
`systems` 84 → 42/21/21 is fine, but `cot_prompts` is **6** (→ 2/2/2) and
`rag_prompts` is **9** (→ 3/3/3). With `COT_P = 0.2`, a 25-config `S_val`
holds ~5 CoT-bearing configs drawn from a 2-element pool — that re-opens
**exactly the A5 question** (a disjoint split of a tiny value set creating a
worse confound than the leakage it removes). **Call 3** in the full plan puts
three options up; I recommend 3-way on `systems`+`temperature` with
`cot`/`rag` split *two* ways (`build`-disjoint, `val`/`test` sharing), since
the leak I2 exists to prevent is `build` seeing the evaluation pools. **I
will implement whichever is approved and will not pick one unilaterally.**
Either way the config-schema change is an **I7 event**.

**F3 — a third silent defect in `sample()`, same class as D005's two.** Its
docstring promises "n **unique** confs" and it dedups via `set()`, but
`PromptConf` defines neither `__eq__` nor `__hash__` (verified: absent from
`__dict__`), so identity hashing means no `add` is ever rejected and the loop
deduplicates **nothing**. Measured over 40 seeds at C4's sizes: `S_build`
(n=75) carries **mean 3.95 duplicate configs** (max 8), and **33% of
duplicates land in the "bare" cell** (no system/CoT/RAG) which is only 6.2%
of draws — they concentrate where the fewest dimensions distinguish configs.
This does not invalidate D005 (its test checks drawn *indices*, unaffected),
but it means `S_build` is effectively ~71 distinct configs, baked in by I6.
**Call 4:** the dedup *key* is a judgment call — I recommend
`(raw, sampling_hparams)`, since `rag_prompt` is materialised with a random
document and keying on the materialised string would leave the bug in place
under a new name.

**F4 — the wall-clock guardrail is ~2× optimistic and would false-alarm on a
healthy run.** The shard unit is one model, so makespan is
`ceil(37/20) = 2` rounds × per-shard time, not node-hours ÷ 20. Per shard =
29,125 generations = **3.3–3.6 h** (100 tok) / **5.4–6.5 h** (200 tok) →
makespan **6.5–7.2 h** / **10.7–13.0 h**. D006's "4–6 h" is below even the
naive division. **This figure is originally mine** — my 2026-09-04 estimate
divided 85 node-hours by 20 slots, which is a *utilisation* number, not a
makespan; design side rescaled the node-hours to 37 models in good faith
while the makespan didn't inherit the rescale. Correcting it here. Also
omitted: **~478 GB of weight downloads** across 37 shards, and the fact that
D002 measured only 3B/7B while the universe spans 0.5B–14B (D002's own
"throughput does not track parameter count" makes flat extrapolation
reasonable, but it *is* an extrapolation and R will say so). **Proposed
replacement guardrail: 20 h wall-clock / 350 node-hours.**

**F5** — quote cost per-query (~0.52–0.57 node-h/query at 100 tok), since S2
grows `Q_0` by 20–40 tokenizer probes (+9–17%) after the guardrail was set.
**F6** — the S5 manifest should pin each model's **HF revision SHA**;
`llm.py:38` passes no `revision=`, so shards resolve whatever `main` is that
day. Free now, unrecoverable later. Folded into Call 2.

**Call 1 (tokenizer probes):** 26 concrete instances proposed across
`digit-chunking` (7), `whitespace-merging` (6), `unicode-byte-fallback` (7),
`glitch-token` (6) — full text in the plan. Two caveats on record: the glitch
tokens are GPT-2/NeoX-vocabulary artifacts and **none of the 37 models uses
that tokenizer** (fine here — a probe earns its place by `Sep(·,·)`, not by
glitching — but R must not describe them as "known glitch tokens"); and
`RAG_P = 0.2` wraps some probes in retrieved context that may swamp them.

**Call 2 (reassembly):** manifest schema (incl. F6's revision pinning), an
explicit freeze point (`status: PARTIAL` until all 37 shards validate, and
that field is what downstream checks), and **all-37-or-nothing** for anything
computing `Sep(·,·)` — because `CVaR_γ` is a *tail* statistic over the pair
set, so dropping one model deletes 36 pairs and changes what the tail is. A
35/37 corpus is a different experiment, not a smaller one.

**Agreed without objection:** generating all 125 configs in one pass (D006's
collection-time vs analysis-time argument is right, and nothing about I2 is
weakened by collecting `S_test` early); sharding as mandatory (re-verified
live: `qgh` MaxWall 2-00:00:00, MaxJobsPU 20, MaxSubmitPU 40 — the last means

**Ready to start on approval of Calls 1–2 alone: S1 (batching fix + C7
