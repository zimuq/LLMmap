## Part 0 — The premise check, because D011 is built entirely on one D008 sentence

D008/R10 said: *"33 of the 37 have an oracle ≥ 0.95 — some query in the pool
separates them nearly perfectly and selection missed it."* D011's `source:` and
outcome table both take that as given. But D008's own artifact carries a caveat
its `## R` narration dropped: the oracle is `max over all 259 queries of TEST
accuracy`, **selected on the evaluation split**. With 50 eval traces per pair, a
max over 259 noisy estimates is inflated by construction — the winner's curse
D007/F2 already corrected for once in this project.

Measured, using the same fix (select on one half of the 25 test configs, evaluate
on the other):

| criterion | pairs ≥0.95 | mean |
|---|---|---|
| **naive oracle** — max over 259, all 25 configs *(D008's reported number)* | **33 / 37** | 0.977 |
| **honest oracle** — pick `q*` on half A, score on half B | **18 / 37** | 0.908 |
| **split-half robust** — best query clearing the bar on *both* halves | **32 / 37** | 0.970 |
| median query (no selection at all) | — | 0.811 |

**Mean shrinkage naive → honest: +0.069.**

**Reading this honestly, in both directions:**

- The concern was right in mechanism. D008's per-pair oracle figures are
  **optimistic by about 7 accuracy points**, and "18/37" is what an unbiased
  point estimate of the selected query looks like.
- **But the qualitative claim survives.** Requiring a query to clear 0.95 on two
  *independent* halves — which noise cannot fake twice — still passes **32 of 37**
  pairs. So "for almost all of these pairs, the pool does contain a query that
  separates them very well, and the per-pair argmax missed it" is a real finding.
- The honest-oracle column (18/37) is itself downward-biased: 12 configs is 24
  traces, so clearing 0.95 needs 23/24. The truth is bracketed by 18 and 32, and
  the 32 figure is the more informative bound because it demands consistency
  rather than a single lucky split.

**Proposal: D011 proceeds, and `R` restates the headline as "32 of 37 under a
split-half-robust criterion", retiring the bare "33" with its ~7-point optimism
noted.** The premise is sound; the number was not.

## F1 — D008's flagged pairs have **nothing to do with `GreedyCover`'s chain**

D011's `## D` describes the 33 as pairs where *"no query in `GreedyCover`'s
selected chain separates them well, but a near-perfect query exists elsewhere in
the 259-query pool."* That is not what D008 computed. From
`experiments/d008_frontier.py:95`:

```python
qstar = S.argmax(axis=0)          # argmax over ALL 259 queries, per pair
```

`GreedyCover`'s chain never enters that script. The T2 flag means: **the single
query the build tensor ranks highest for this pair gives <75% 2-way test accuracy,
while some other query does much better** — a *per-pair* selection error, not a
consequence of an 8-query shared budget.

**Two concrete consequences for the plan as drafted:**

1. **S4's stated sanity check is not valid.** D011 says *"(a) should mostly fail —
   that is exactly why these pairs were flagged."* It is not why they were flagged.
   Nothing about T2 constrains what `GreedyCover`'s 8 queries do on these pairs, so
   (a) failing is not a methodology check and (a) *succeeding* is not a bug. The
   `GreedyCover` chain's performance here is an ordinary empirical question with no
   pre-committed direction — and it is the right baseline, exactly as S4 intends,
   just not for the reason S4 gives.
2. **The comparison D011 actually wants is still well-posed**, and arguably more
   interesting under the corrected premise: *the per-pair argmax (an oracle-style,
   one-query-per-pair selector) missed these; does either shared 8-query chain
   catch them anyway?*

Logged to `TACC_NOTES` since `## D` is design-side owned. **Not blocking** — the
steps still run; only S4's rationale and `R`'s framing change.

## F2 — S2's threshold is on a different scale from the criterion that produced the pairs

D011/S2 says to check `max over JointGreedy's 8 queries of S_energy[q][pair]`
against *"the same threshold θ D008/S7 used to originally flag these pairs."*
D008/S7 has three θ's and they are not interchangeable:

| tier | θ | scale |
|---|---|---|
| T1 | 0.1303 | `S_energy` (self-pair null) |
| **T2 — the tier these 37 pairs come from** | **0.75** | **2-way test accuracy** |
| T3 | 0.8761 | `S_energy` (5th percentile) |

The 37 pairs are **T2's**, so "D008's θ" for them is an *accuracy* threshold; there
is no `S_energy` θ that flagged them. Applying T1's or T3's number to a max over
the chain would answer a different question and quietly change the population.

**Proposal: run criterion (a) on T2's own accuracy scale** — 2-way test accuracy,
θ = 0.75, D008's own proxy classifier (`d008_lib.two_way_correct`) — and report the
`S_energy` view (T3's 0.8761) alongside as a secondary, clearly labelled. That
keeps (a) directly comparable to how the pairs were flagged instead of nearly so.

## Call 1 (design side) — the threshold for criterion (b)

D011 asks how to threshold the joint statistic, noting its scale differs, and
suggests a percentile of its own distribution.

**Proposal: don't introduce a joint-statistic threshold as the primary at all.
Put (a), (b) and the original T2 flag on one scale — accuracy.**

- **(a)** = `max` over the chain's 8 queries of **single-query** 2-way test
  accuracy ≥ 0.75.
- **(b)** = the **set's** 2-way test accuracy ≥ 0.75 **while (a) fails** — i.e. the
  8 queries together resolve a pair that none of them resolves alone. Computed with
  D008's own machinery (`d008_lib.summed` over the chain, then `two_way_correct`),
  so it is the same classifier, same split, same threshold as the flag.

This gives exactly the (a)-vs-(b) distinction D011 says is the point of the D, with
no new threshold invented and nothing on an incommensurable scale.

**Secondary, mechanism-level view** (kept because D011 asks about the *statistic*,
not only the outcome): the joint statistic over the chain, thresholded against a
**self-pair null computed at `k=8`** — the same construction D008/Call 3's T1 used,
and the machinery already exists from D010's pilot. Percentile-of-its-own-
distribution is the one option I'd argue against: as D008/Call 3 already noted, a
percentile threshold fixes its own answer's size by construction.

## F3 — Don't repeat the mistake Part 0 just diagnosed

Criterion (a) takes a **max over 8 queries**, so it carries a small winner's curse
of its own. The chains themselves are clean — both were selected on `S_build`, so
evaluating them on test involves no selection on test — but (a)'s max does.

**Proposal: report (a) both naively and split-half** (pick the best-of-8 on half A,
score on half B), exactly as Part 0 did. With 8 candidates instead of 259 the
inflation should be small; measuring it costs nothing and this D is precisely a
lesson in not assuming that.

---

## F4 — "Non-trivial share" needs a number before the count exists

D011's CONFIRMED branch says *"resolves a non-trivial share"* without saying what
that is. Pre-registering, so the threshold isn't chosen after seeing the count:

- **≥ 12 of 37** recovered by `JointGreedy` **beyond** what `GreedyCover`'s chain
  recovers → CONFIRMED (meaningful recovery).
- **≤ 4 beyond** → NOT RECOVERED.
- in between → PARTIAL/MIXED, reported per-pair.

And per D011's own emphasis: **the (a)/(b) split is reported regardless of which
branch fires**, because a recovery that is entirely (a) means something different
from one that is even partly (b).

## Failure handling

- **Both chains recover ~everything**: then T2's 37 were a per-pair-argmax artifact
  rather than a hard-pair set, and `R` says that — it would substantially weaken
  D008's frontier framing, which is worth knowing.
- **Neither chain recovers anything**: NOT RECOVERED; the 33/32-pair gap stands
  where D008 left it and Phase 3's motivation is untouched.
- **(b) never fires for either chain**: report it — it would mean set-level
  resolution beyond the best single member does not occur at this `k` on these
  pairs, which is a direct, negative answer to D010's mechanism question.
