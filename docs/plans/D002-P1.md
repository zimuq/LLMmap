## 0. Recon already completed (read-only; no environment changed)

Per D002's code-change rule, nothing was installed or modified. The following is
from Slurm introspection, the TACC Vista user guide, and repo code reading.

### F1 — D001/P1 §F5 was wrong, and this is the main finding

D002 asks whether missing GRES is "a wrong partition/wrong-build problem, or is GPU
genuinely unavailable." It is **neither** — it is the documented, intended
configuration:

- Each **GH node has one NVIDIA H200 GPU with 96 GB HBM3**, plus a Grace CPU with
  116 GB LPDDR.
- The TACC Vista guide states **Vista does not support `--gres` or
  `--gpus-per-task`, and Slurm will reject any job script containing them.** GH
  nodes are allocated exclusively, so the GPU is simply available — no GPU flag is
  needed or permitted.

`scontrol show node` confirms `Gres=(null)` on every partition, which under this
scheme is expected rather than symptomatic.

> **Correction to the record.** D001/P1 §F5 inferred "no GPU" partly from absent
> GRES. That inference was unsound: GRES absence is how Vista is configured, not
> evidence of a missing accelerator. The **only** real cause of D001 running on CPU
> was the CPU-only wheel (`torch 2.7.1+cpu`) installed during environment
> bring-up. D001's results are unaffected (it is a small CPU job either way), but
> the follow-up framing "GPU access appears broken" in D001's Review overstates the
> problem. Expected D002 verdict is **GPU_AVAILABLE**, pending the empirical
> confirmation in S1 — which is exactly why M2 demands an on-device check rather
> than inference from docs or `pip list`.

### F2 — Partition map

| Partition | Nodes | Cores | GPU | Notes |
|---|---|---|---|---|
| `gh` | 576 | 72 | 1× H200 96GB | main GH200 queue |
| `gh-dev` | 20 | 72 | 1× H200 96GB | 2h cap, QoS `qdevelopment`, **1 job/user** |
| `gg` | 251 | 144 | **none** | Grace-Grace, CPU-only *by design* |
| `gb` | 18 | 144 | Grace-Blackwell | not covered in the user guide |

Targeting `gg` would produce exactly the "no GPU" symptom legitimately. Our jobs
went to `gh-dev`, which does have an H200.

### F3 — Software available

CUDA modules `11.8 / 12.4 / 12.5 / 12.6 / 12.8`. **No** PyTorch module.
`tacc-apptainer/1.4.1` is available as a container fallback. The current `llmmap`
conda env holds `torch 2.7.1+cpu`.

### F4 — Generation prerequisites

`LLM_huggingface.__init__` **raises** unless `HUGGINGFACE_API_KEY` is exported
(`LLMmap/llm.py:23-25`) — required even for ungated repos. Gated repos
(Llama, Gemma, Mistral) additionally need license acceptance on the HF account.
`load_llm` passes `device_map="auto"` (`llm.py:189`), so with a CUDA build the
target model lands on the GPU automatically. Default `max_new_tokens = 100`
(`llm.py:9`).

### F5 — Throughput finding that likely dominates the Phase-1 cost answer

`make_dataset_entries_for_new_llm` generates **strictly one prompt at a time**:

```python
# LLMmap/dataset_maker.py:36-39
for query in queries:
    prompt, sample_params = prompt_conf(query, llm)
    o = llm.generate(prompt, sample_params)[0]
```

but `LLM_huggingface.generate` already accepts batched input (`padding=True`,
`batch_decode`, `llm.py:74-89`). Batch-1 autoregressive decoding leaves most of an
H200 idle. The batched-vs-unbatched ratio plausibly decides whether Phase 1 is
affordable, so **M3 measures both**. Batching the 8 queries *within* one prompt
config is safe (identical sampling params); batching across configs is only valid
where params coincide.

This plan measures the gap and reports it. It does **not** modify
`dataset_maker.py` — any such change belongs to the Phase-1 D, with its own review.

## 1. Steps

### S0 — Prerequisites (disclosed environment changes)

1. **New conda env `llmmap-gpu`** (conda-forge, Python 3.11), `requirements.txt`
   plus a CUDA aarch64 torch wheel:
   `pip install torch --index-url https://download.pytorch.org/whl/cu126`.
   **The existing `llmmap` env is left untouched** so D001's CPU numbers stay
   reproducible; ~3 GB extra on `$WORK`.
2. `export HUGGINGFACE_API_KEY=<token>` (F4). **Needs the human** — see §5.
3. **Pre-stage model weights from the login node** into
   `$WORK/vista/.cache/huggingface`. Compute-node external egress on Vista is
   untested; downloading on the login node removes that risk from the timed run.

### S1 — M1 + M2: prove the GPU is real and used

One `gh-dev` job. **No `--gres` / `--gpus-per-task`** (F1: Slurm rejects them).

- `nvidia-smi` → device present, name, memory, driver.
- `torch.cuda.is_available()`, `get_device_name()`, `get_device_capability()`.
- **On-device op, not an inference from `pip list`** (M2's explicit requirement):
  allocate a tensor, assert `t.device.type == 'cuda'`, run a matmul, assert
  `torch.cuda.memory_allocated() > 0`, and check the result against a CPU
  reference.
- Log driver/runtime CUDA versions for the audit trail.

*If `torch.cuda.is_available()` is False on a `gh` node* → that is the
GPU_UNAVAILABLE branch; go to S4.

### S2 — M3: throughput benchmark

Two **ungated** models, both already in D001's 52-model universe, chosen to span
the size range while avoiding gated-repo risk (F4):

| Model | ≈ weights | Role |
|---|---|---|
| `Qwen/Qwen2.5-3B-Instruct` | ~6 GB | small end |
| `Qwen/Qwen2.5-7B-Instruct` | ~15 GB | mid end |

Stand-ins per D002's scope limit: the paper's existing 8 queries
(`confs/queries/default.json`) × 10 prompt configurations sampled via
`PromptConfFactory` from `confs/prompt_configurations/`. 80 generations per model
per regime.

Measured per model: wall-clock, generated tokens/sec, per-generation latency,
peak GPU memory (`torch.cuda.max_memory_allocated`), and model load time
(separated from generation time — it is a per-model fixed cost that matters at
|L|=25).

Run **two regimes**: (a) unbatched, matching current `dataset_maker.py`; (b)
batched at 8 (the queries within one config). Report the speedup ratio.

Reuses `load_llm`, `PromptConfFactory`, and `LLM_huggingface.generate` — a new
benchmark script only, no repo code modified.

### S3 — M4: extrapolation to Phase-1 scale

Cost model, stated explicitly so reviewers can substitute their own assumptions:

```
generations = |L| × |Q_0| × n_configs
GPU-hours   = Σ_models (|Q_0| × n_configs / throughput(size)) + |L| × load_time
```

Table over `(|L|, |Q_0|) ∈ {20×80, 25×100, 30×120}`, with `n_configs = 125`
(C4's 75/25/25 — flagged as itself undecided), under both regimes from S2 →
`results/D002/cost_extrapolation.csv`.

Also report a **storage** line: ~25 models ≤14B at ~2 bytes/param is roughly
300–400 GB of weights against ~850 GB free on `$WORK`. Feasible, but it is a real
A1 constraint and belongs in the sizing answer.

### S4 — M5: CPU fallback (only if S1 fails)

Same benchmark on CPU, same extrapolation table, plus an explicit recommendation
for how far `A1`/`C3` must shrink.

### S5 — Write R

Verdict + confidence + concrete `A1`/`C3` recommendation into `docs/D002.md` `## R`,
data under `results/D002/`. R must state the F1 correction so the "GPU access
appears broken" follow-up is closed accurately in the project record.

Not run on a login node.

## 3. Failure handling

| Failure | Response |
|---|---|
| Slurm rejects the job over a GPU flag | Expected if one were used — F1 says none is permitted. Remove it. |
| `torch.cuda.is_available()` False on `gh` | Do **not** patch around it. Record driver/runtime versions, retry once on `gh` rather than `gh-dev` to rule out a dev-queue limitation, then declare GPU_UNAVAILABLE and run S4. |
| CUDA aarch64 wheel won't install/import | Fall back to an NGC PyTorch container via `tacc-apptainer/1.4.1`; report which path worked. |
| Compute node has no external egress | Already mitigated by S0.3 pre-staging; if it still bites, the run is data-local and unaffected. |
| `HUGGINGFACE_API_KEY` unset / repo gated | Benchmark is deliberately restricted to ungated Qwen models. If the token itself is missing, S2 cannot run — escalate rather than substitute models silently. |
| OOM at batch 8 | Halve the batch and record the largest that fits; report memory headroom on 96 GB. |

## 4. Verification

- `nvidia-smi` reports H200 96 GB, consistent with F1.
- CPU-vs-GPU matmul agreement within float tolerance → device math is real.
- Generated text is non-empty and well-formed for both models (guards against
  measuring a broken generation path).
- Batched and unbatched runs produce comparable output length distributions —
  otherwise the speedup is an artifact of truncation, not throughput.
- Throughput is reported with the measured token counts it derives from, so the
  extrapolation can be recomputed from raw numbers.

## 5. Needs the human

`HUGGINGFACE_API_KEY` must be provided (F4) — no HF generation can run without it.
Ungated models avoid the license-acceptance issue, but the token itself is
mandatory. This is the only blocking external input.
