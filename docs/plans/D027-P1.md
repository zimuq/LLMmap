- One read-only step has been done: HF API metadata for all 49 candidates.
  - Covered: access with our token, revision SHA, weight size,
    `architectures` / `model_type`, the `transformers_version` the checkpoint
    was saved with, chat-template presence, template variables (thinking
    switches, date functions).
  - Script: `experiments/d027_hf_prefacts.py`. Output:

  - The same pass confirmed that all 37 v1 repos are still accessible and
    that none has moved from its D006 revision.
- **Unlike D025/D026, S0 is not run before this P.** It needs a new conda

  action. P is approved first; S0 then runs and reports its survivor list
  for a second approval, as the D requires.

**Headline: engineering findings the D did not anticipate.**
1. **`build_configs()` is not deterministic across processes** (Call 1;
   `TACC_NOTES` Issue 21).
   - Two fresh processes return two different 125-config draws (sha
     `45ed34a2…` vs `21c90667…`).
   - The cause is the `set()` dedup in `PromptConfFactory.sample` under
     Python hash randomisation. The seed only fixes the RNG, not the set's
     iteration order.
   - This is the root cause of Issue 18 (36/37 v1 models got different
     configs).
   - The D's "same seed, so every model sees the same 75+25 configs as v1"
     **does not hold**, and rerunning it would give the regenerated v1
     models *new* configs.
2. **Templates render today's date** (Call 3), via `strftime_now`:
   - v1: Llama-3.2-1B/3B and granite-3.1;
   - candidates: Mistral-Small-2501/3.1 and granite-3.2/3.3.

   A regenerated v1 model would see a different prompt from `corpus_v1`,
   and the screen would not be reproducible day to day.
3. **Thinking switches are not uniform** (Call 4):
   - granite-4.2 defaults to thinking **on** (`enable_thinking` defaults to
     True; it must be passed);
   - granite-3.2/3.3 use a different variable (`thinking`, default off);
   - Qwen3 / Qwen3.5 / gemma-4 use `enable_thinking`.
4. **The required stack is transformers ≥ 5.10** (Call 2).
   - The highest saved-with versions: gemma-4-12B 5.10.0.dev0, gemma-4-E4B
     5.5.0.dev0, Ministral-3 5.0.0.dev0, Qwen3.5 4.57.0.dev0.
   - The current env is 4.51.3. That is a major-version jump for the
     regenerated 37 too, and it affects tokenisation, `generate` defaults
     and remote code.
5. **Byte-identity drift (secondary (f)) would be confounded by batching**
   (Call 5).
   - D026 S0 measured that just regrouping the same queries changes ~30%
     of greedy outputs under the *same* env.
   - The screen batches `paper8` differently from `corpus_v1`'s 64-query
     chunks of 259.
6. **Access:** tiny-aya-global and tiny-aya-fire are **not yet accepted** on
   our HF account (auto-gated). Human action. gemma-3 ×3 and EuroLLM-9B are
   already accessible.
7. **Mistral-Small-3.2 has no `tokenizer_config.json` and no HF template.**
   It will be dropped by rule 6 in S0. Its N-neighbours (#20, #21) survive.

## Calls

### Call 1 — configs: replay v1, freeze new draws (needs design-side; the D's premise is wrong)

**Facts.**
- `build_configs()` called in two processes gives two different draws.
- With `PYTHONHASHSEED=0` it is stable (sha `560b82ce…`), but that is not
  what D006 ran.
- `corpus_v1` stores each model's own `prompt_conf` per `(pool,
  config_index)`, including the materialised RAG document.

**Recommendation:**
- **(a) Regenerated v1 models replay their own `corpus_v1` configs** through
  `PromptConf.from_dict`, exactly as D026 S0 did.
  - The screen's v1 rows then differ from `corpus_v1` only by environment and
    batching.
  - D028 inherits the v1 test configs unchanged.
- **(b) Each new model gets its own full 125-config draw** (75/25/25), the
  same per-model mechanism v1 effectively had.
  - Seed: `random.seed(f"20260906:{model}:{pool}")`, in a process with
    `PYTHONHASHSEED=0`.
  - **Frozen to `data/corpus_v2_screen/configs/{slug}.json` in S0, before
    S1**, with sha256s in the manifest.
  - The 25 S_test configs are drawn and frozen too, never generated, so
    D028 uses them without a redraw.
  - I2: every draw comes from the same per-pool universes (`split_v2`),
    asserted pool-disjoint per parameter, with the A7 "no system prompt"
    carve-out.
- **Alternative:** one shared draw for all 49 new models. Rejected: it would
  make new models config-aligned while v1 models are not, an asymmetry
  inside one universe.

### Call 2 — the environment (needs design-side)

- **`llmmap-gpu-v2`, as a venv over a fresh conda env**, never by
  installing into `llmmap-gpu` (ENV.md discipline 3).
  - Proposed pins: `transformers==5.18.0` (newest; needs torch ≥ 2.5,
    huggingface-hub ≥ 1.31, tokenizers ≥ 0.23.1).
  - `torch==2.7.1+cu128`, *kept the same as v1*, so the env change is
    transformers/tokenizers/hub only.
  - Plus `mistral_common` only if a surviving Mistral model needs it for
    its HF template (it should not).
  - Exact `pip freeze` recorded in `s0.json`.
- **The new env is for generation only.** I5 embedding, B0′ training, the
  linear and 1-NN readouts all stay in **`llmmap-gpu`**, using the D006 /
  D009 code unchanged.
  - Reason: I5 is frozen, and a transformers 5 forward pass of e5 could
    move embeddings.
  - Reason: the instrument control compares with D025, which was trained in
    `llmmap-gpu`.
  - The D says "one new environment for every generation". This reading
    keeps everything *downstream* of generation identical to v1.
- **v1 models that fail in the new env.**
  - At risk: DeciLM-7B (remote code); internlm2.5 (remote code +
    sentencepiece 0.1.99, which the D already exempts); the Together
    Llama-2-32K template fallback (a v1 exception, kept).
  - **Recommend:** generate such a model in its D006 env (`llmmap-gpu` or
    `llmmap-internlm`), with `gen_env` recorded per row, rather than drop
    it. v1 models cannot leave the universe.
  - Its drift row (f) is then trivially "old env", and R names it.
- **Kernel-free paths are expected for the hybrid architectures**
  (Falcon-H1 Mamba2; Qwen3.5 linear attention). There are no aarch64 wheels
  for `mamba-ssm`, `causal-conv1d` or `flash-linear-attention`, so they run
  on transformers' torch fallback. That is slower, not wrong. Preflight
  measures gen/s; nothing is compiled.

### Call 3 — freeze the template date (needs design-side; prompting decision)

- Pass `strftime_now = lambda fmt: datetime(2026, 9, 6).strftime(fmt)` as a
  template kwarg.
  - Template variables shadow the jinja global of the same name.
  - Also pass `date_string = "06 Sep 2026"`, for Llama-3.x-style templates.
- **2026-09-06 is the date every date-rendering v1 shard was generated**
  (Llama-3.2-1B/3B and granite-3.1 all started and finished 2026-09-06), so
  v1 replay is faithful.
- New models get the same fixed date.
- Recorded in the row's `template_kwargs` (as the date string).
- S0 asserts that the rendered prompt contains the fixed date wherever the
  template used to render today's.

### Call 4 — thinking off: one kwarg set for every model (needs design-side; rule 4 wording)

- **Template kwargs for every model:** `enable_thinking=False,
  thinking=False`. Both are ignored where unused.
  - granite-4.2 (`enable_thinking` defaults to **True**) needs the first.
  - granite-3.2/3.3 call the switch `thinking` (default off), not
    `enable_thinking`. Strictly, rule 4 says "accepts `enable_thinking=False`".
  - TACC reads rule 4 as "**a template switch** turns thinking off". The
    alternative would drop granite-3.2/3.3 on a variable name, and their
    default is already off.
- **Output check as the D specifies.** Decode once with
  `skip_special_tokens=False` and scan for:
  - `<think`, `</think>`, `<|think|>` (gemma-4), `<|channel|>`,
    `<reasoning`;
  - plus every think-like tag found in that model's template (recorded in
    `hf_prefacts.json`: Qwen3 / 3.5, granite-3.3 / 4.2).
- Empty `<think></think>` blocks in the *prompt* (Qwen3 / 3.5 with the
  switch off) are expected and recorded.

### Call 5 — environment drift (f): measure it so D028 can use it (needs design-side)

- **The problem.** Comparing screen outputs with `corpus_v1` mixes three
  things:
  - the env change;
  - batch composition (D026: ~30% of greedy outputs change from regrouping
    alone);
  - for new-config models, configs. Call 1(a) removes this one for v1.
- **Recommend (f) as two numbers per v1 model**, measured in the same S1
  job while the model is loaded:
  - **(f1) Exact-batch replay.**
    - 2 greedy S_build configs per v1 model (D024's tier-1 greedy reference
      first, then the lowest index).
    - All 259 queries at batch 64, exactly D026 S0's method, in the new env.
    - Byte-identical rate vs `corpus_v1`. This is **pure env drift**, the
      number D028 needs to decide whether v1 259-query shards are reusable.
    - Cost ≈ 37 × 518 ≈ 19k gens, ~1 node-h.
  - **(f2) Tokenisation parity**, CPU, in S0.
    - Every `corpus_v1` prompt of every v1 model, rendered and tokenised in
      both envs (with Call 3's date).
    - Count of prompts whose token ids differ. This separates tokenizer
      drift from numerical drift.
- **Both are descriptive** (no stop rule, as the D says).
- Byte identity is the strict end, so R also reports (f1) as a
  distributional check: the 1-NN two-way accuracy of old-env vs new-env
  responses on those configs. Near chance means the same distribution.

### Call 6 — batching, packing, sampling seeds (disclosure; design-side may object)

- **Cross-config packing.**
  - The harness batches within a config. `generate` takes one
    sampling-kwargs set, so configs may share a call **only if their
    `sampling_hparams` are identical**. `corpus_v1` has 14 distinct sets
    across its 100 build+val configs.
  - S1 packs each identical-hparams group into calls of ≤ 64 prompts
    (8 configs × 8 queries), in config-index order.
  - Batch 64 is 6.2× batch 8 (D006/S1c, Phi-3-medium): about 9 min saved per
    model (800 gens ≈ 10.5 vs 1.7 min).
  - Packing changes batch composition. This is the nuisance D026 measured
    (symmetric across models, and v1 replay rows in the screen get it too).
    So (f1), not the screen rows, carries the drift claim.
- **Seeds:** `torch.manual_seed` per (model, pool, config-group).
  `corpus_v1` used none.
- **OOM:** halve the batch for that model only, as the D allows. Disclosed
  per model in its status file.
- **Padding sanity for non-attention architectures** (Falcon-H1, Qwen3.5),
  in preflight:
  - greedy `paper8` on one config, batched vs one prompt at a time;
  - exact-match rate reported next to the attention-model baseline (D026:
    ~70%);
  - a model whose batched outputs are degenerate (empty or repetitive
    where unbatched are not) is a Call, not a silent drop.

## Cost (projection; S0 replaces it with measured gen/s)

| item | basis | node-h |
|---|---|---|
| staging | login node, ~850 GB | 0 SU (wall time several hours) |
| S0 preflight | 85 loads (~1.4 TB read) + 3 configs × 8 q each | ~3–4 |
| S1 screen | 85 × 800 gens. Batch-64 ≈ 6 gen/s for ≤ 14B; MoE / 32B / hybrid slower, assume 1–2 gen/s | ~6–9 |
| S1 (f1) replay | 37 × 518 gens | ~1 |
| S1 embed | ~68k + 19k rows, I5 | < 0.5 |
| S2 | 5 attention seeds on ~85 classes + linear + 1-NN | ~1–2 |
| **total** | | **≈ 12–17 node-h**. The D expects ≲ 40, and its Call threshold is 60 |

- **Job packing matters for SUs.** There is a 15-minute minimum per job, so
  one job per model would cost ≥ 21 node-h in floors alone. Bucketing by
  size (~10 jobs) avoids that.
