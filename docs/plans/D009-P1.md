# P1 — Execution plan for D009 (closed-set accuracy under LLmap's own trained pipeline)

**Status: PROPOSED — awaiting review.** `gate: REVIEW`. The cost pilot D009's
Cost constraint explicitly authorises has been run (job 984685); nothing else has.
**No existing repo file has been modified.** New files only, listed under
"Code-change disclosure".

The headline from the pilot: **a training run costs 8.7 seconds**, `train_model`
runs **unmodified**, and the paper's 8 queries at `k=8` reach **0.8346 test top-1**
(chance 0.027). So Call 1's cost/coverage trade-off largely dissolves — the full
`k=1..8` grid is affordable — and D009's S4 sanity gate is already known to pass.

## S1 is already done, at zero cost, and cannot drift

D009/S1 asks for the selected queries' embeddings. **D006/S6 already embedded all
259 pool queries** — `data/corpus_v1/embeddings/_queries.npy`, with
`_queries.index.json` recording the I5 model, the pooling, and `q0_sha256`
matching `pool_v1.json`. Its own comment says it was done because "the pipeline
consumes both". Verified in the pilot: shape (259, 1024), sha matches.

So S1 becomes a *verification* step, not a compute step, and — more usefully — the
query embeddings provably come from the same run as the response embeddings, so
they cannot silently diverge from them.

## Call 1 (design side) — which `k` values to train

**Proposal: the full grid. `k = 1..8` × 4 conditions × 5 seeds = 160 runs ≈ 25 min
of GPU, plus ~5 min of trace assembly.**

D009 suggested a representative subset (`k∈{1,2,4,8}`) might be enough and asked
for a measured cost before committing. At 8.7 s/run the subset saves ~12 minutes
and costs us the shape of the curve — and the *shape at small `k`* is precisely
where D008's finding lives (CVaR's advantage is +0.13 at `k=1` and gone by `k=5`).
Subsampling `k` here would blur the one region the D exists to check.

---

## Call 2 (design side) — how many random draws / seeds

**Proposal: 5 runs per condition per `k`, and the two variance sources kept
distinct.**

- **`random`**: 5 of **D008's own draws**, indices 0–4 from
  `results/D008/random_draws.json`, used verbatim (no re-draw — I6 covers the
  selection outputs). One training seed each. The resulting band therefore
  contains *both* draw variance and training variance, which is what a baseline
  band should contain.
- **`cvar_max`, `mean_greedy_max`, `paper8`**: the query set is fixed, so the 5
  runs are 5 **training seeds** — `{0,1,2,3,4}`, the identical set for every
  condition, so condition comparisons are paired on seed.

D008 used 200 random draws because a nearest-neighbour classifier is free; 200
trainings is not the right transfer of that decision. 5 is small, and P states the
consequence rather than hiding it: **the random band's endpoints are noisy**, and
any conclusion resting on `random`'s exact percentile rather than on its rough
level should be marked as such in `R`.

---

## F1 — Training-seed variance is not optional here

**One run per condition would conflate "which queries" with "which
initialisation", and D009's whole question is the first of those.** The pilot's own
numbers show why the margin matters: paper8 `k=8` scored 0.8346 on test and 0.8551
on val from a single seed, and D008 established that worst-class on 25 test configs
moves in 4-point steps with ±0.20 CIs.

**Proposal (folded into Call 2): 5 paired seeds per condition per `k`, reporting
mean and full range, with the seed range shown alongside every condition-vs-condition
delta.** A delta smaller than the seed range is reported as *not resolved by this
experiment*, pre-registered now rather than argued afterwards.

---

## F2 — The shipped `train.py` early-stops on the split it reports; we will not

`train.py` calls `train_model(..., loader_test=loader_test)`, and inside
`trainer.py` that loader is what `EarlyStopping(monitor="val_loss")` and
`ModelCheckpoint(monitor="val_loss")` consume. **The shipped procedure therefore
selects its checkpoint on the same split whose accuracy it then reports.**

Per the human's instruction (2026-09-09) that "尽可能还原" means reproducing the
pipeline, not reproducing its unreasonable choices, **P1 uses `S_val` (25 configs)
for early stopping and checkpoint selection, and touches `S_test` exactly once, at
S5** — which is also what I2 requires and what every prior D in this project did.

Stated plainly because it cuts against us: **our numbers will be lower than the
shipped procedure would produce on the same data.** The pilot shows the size of
that gap at one point — val 0.8551 vs test 0.8346, ~2 points.

## F3 — `test_model.py` cannot measure closed-set accuracy (not used here, disclosed)

`evaluate_topk` ranks with `np.argsort(distances)[:k]` — ascending, i.e. smallest
first. That is correct for `InferenceModel_open`, whose `__call__` returns
*distances* to templates. `InferenceModel_closed.__call__` returns **softmax
probabilities** (`inference.py:125`), where larger is better, so the same line
selects the `k` **least** likely classes.

D009 does not use that script — S5 reads logits from the trained network directly
— so this is **disclosed and logged (`TACC_NOTES`), not patched**: patching an
unused script inside a REVIEW-gated D would be a code change the D did not ask
for. Flagging it because "compute closed-set accuracy with the shipped tooling" is
a natural next instinct and it would return a near-zero number.

---

## F4 — The 650-char truncation is inference-only, and it is label-correlated

`inference.py:118` truncates every answer to `conf['max_number_chars_response']`
(650) **at inference time**. `dataset.py`'s `EmbeddingCache` embeds the raw
response **at training time**. Measured on our corpus (job 984640,
`results/D008/recon_650char_skew.json`):

| | |
|---|---|
| responses over 650 chars | **52.2%** of 1,197,875 |
| …restricted to the paper's 8 queries | 34.2% of 37,000 |
| median response length | 700 chars (the threshold sits at the median) |
| when truncated, share of the response kept | 69.4% |
| **per-model range** | **14.3%** (Llama3-ChatQA) → **92.7%** (Llama-2-7B-32K) |

The per-model spread is the part that matters. A deployed `InferenceModel` sees a
distribution shifted from its training distribution **by an amount that varies
6.5× across the very labels it must separate** — for a fingerprinting task that is
not a wash, it is label-correlated shift.

**D009 is unaffected**: S5 evaluates the trained network on assembled traces, i.e.
under the training-path convention (untruncated), consistently for every
condition. But the number we report is "accuracy under the untruncated
convention", and `R` will say so. **Proposal: log this to `PAPER_DEVIATIONS.md`**
(design-side owned, so flagged rather than edited).

## F5 — Bypassing `load_datasets`, verified numerically rather than asserted

The shipped loader takes raw text and re-embeds through `EmbeddingCache`. We
already hold every response embedding (D006/S6) and every query embedding (same
run). Re-embedding would cost a GPU pass per condition × `k` and would risk
producing embeddings that differ from the ones D004–D008's numbers rest on —
exactly what I6 exists to prevent.

So `d009_lib.build_traces` assembles from the frozen arrays. The pilot checked that
this produces the shipped loader's tensor, on 6 entries at `k=8`:

| | |
|---|---|
| cosine | **0.99999970** |
| max abs diff | 2.74e-3 |
| median relative diff | 6.6e-4 |

The residual is fp16 storage (D006/S6 stored fp16; the shipped path recomputes in
fp32) — a property of the frozen corpus, not of the assembly. **The training loop
itself is not bypassed**: `LLMmap/trainer.py` and `inference_model_archs.py` are
used unmodified, per D009's requirement.

## F6 — Two small factual corrections to `METHOD.md §5.5` (flagged, not blocking)

§5.5 describes the trained component as "the projection `f_p: 1024→384` plus the
small self-attention siamese/classifier network, **~8M params**". Measured:

- **3,023,653 params** at `k=8` under `confs/default.json`'s shipped hparams — 2.6×
  smaller than stated.
- The projection is **`Linear(2048 → 384)`**, not 1024→384: it consumes the
  concatenated `[E(query);E(response)]` trace, which §5.5 itself describes
  correctly two paragraphs earlier.

Neither changes the plan. Both go to `TACC_NOTES` since `METHOD.md` is
design-side owned.

## F7 — Open-set is outside D009's scope but inside the human's framing; here is its price

The human's request named "closed-set open-set accuracy"; D009's question, steps
and deliverables are **closed-set only**. Rather than quietly widening the D or
quietly dropping half the request, the cost:

**Open-set is a separate training run per condition, not a free head.** The closed
network's `forward` returns head logits, not the pre-head features `templates.py`
needs, and the open path trains a *different objective* (siamese contrastive) via
`make_siamese_network`. Measured: 70.9 steps/s at 3,907 steps/epoch (the shipped
`num_pairs_per_epoch=500000`) → **0.9 min/epoch, ≤46 min per run** at the shipped
50-epoch cap.

**Proposal: run open-set at `k=8` only, for all four conditions, as an explicitly
separate deliverable — ~3 GPU-hours** (4 runs + `setup_templates`-equivalent
template building + evaluation). That answers the human's question at the one `k`
where all four conditions are directly comparable, without turning a 25-minute D
into a two-day one. **Needs design-side sign-off**: it is scope D009 does not
currently authorise, and I am not folding it in on my own reading of chat.

## Steps

**S0 — Verify frozen inputs.** Corpus manifest `READY` 37/37; `_queries.npy`
(259, 1024) with `q0_sha256` matching `pool_v1.json`; `results/D008/selection.json`
schema `d008-selection-v1` and its recorded tensor sha256; the four conditions'
chains readable. Record all shas in the output.

**S1 — Materialise `results/D009/query_embeddings.npy`** as a copy of D006/S6's
artifact plus a provenance JSON (source path, sha256, the fact that it was not
recomputed). D009 names this deliverable; it should exist under that name even
though the bytes come from D006.

**S2 — Assemble traces** for each condition × `k=1..8` over `S_build`/`S_val`/
`S_test`. Slot order follows the chain's selection order. ~4 s and 182 MB per
`k=8` condition; assembled on the fly per run rather than all 32 written to disk
(D009's `results/D009/traces/` deliverable is satisfied by writing the `k=8` set
per condition plus the assembly code, which reproduces the rest deterministically
— flagged in case design side wants all 32 materialised instead).

**S3 — Train**, `LLMmapTrainerClosed` via the shipped `train_model`, identical
hparams everywhere. **The hparams source is `confs/default.json`'s
`inference_model` block** (the released repo's own configuration), with only
`num_classes=37`, `num_queries=k`, `emb_size=1024` filled in from the data — the
three fields the shipped loader would have filled in itself. The hparams dict is
hashed and the hash asserted identical across every run, so "identical training
procedure" is enforced rather than intended.

**S4 — Sanity check before any comparison.** Per run: train/val loss and accuracy
curves, epochs actually run, and the train−val gap (2,775 samples against 3.0M
params — overfitting is the expected failure mode). Gate: paper8 at `k=8` must
stay far above chance; the pilot already shows 0.8346, so a run that collapses
indicates a bug in *that* run, not a real finding.

**S5 — Evaluate on `S_test`, touched once.** All four `METHOD.md §8` metrics per
condition per `k`, using D008's definitions verbatim so the two D's numbers are
directly comparable: mean top-1; worst-class (plus worst-3, per D008/F3); hard
subset = 2-way restricted accuracy over the **65 structural near-relative pairs**
(D008/Call 2), realised for a 37-way classifier as argmax over just those two
classes' logits; queries-to-reach-X%. Uncertainty: the **same** config-level paired
bootstrap D008 used (`d008_lib.boot_draws`/`boot_metrics`, 2,000 draws over the 25
test configs), plus the 5-seed range.

**S6 — Trained vs proxy, condition by condition, at every `k`.** Delta table
against `results/D008/metrics_by_condition_k.json`, plus the Spearman correlation
of the two `k`-curves per condition. The question is whether the *direction and
rough magnitude* survive, so both the deltas and the curve shapes are reported.

**S7 — Write `## R`:** verdict, four metrics × 4 conditions × 8 `k`, S6's
comparison, S4's sanity results, Call 1/2 dispositions, the hparams source and its
hash, and F2–F7's outcomes.

## Failure handling

- **A run diverges or lands at chance.** S4 catches it per run; re-run that seed,
  and if it recurs report it as a training-stability finding (INCONCLUSIVE per
  D009's own distinction), not as a condition difference.
- **A condition-vs-condition delta is smaller than the 5-seed range.** Report as
  not resolved (F1's pre-registration), not as a null.
- **Severe overfitting** (train ≈ 1.0, val far below): report it as a property of
  the shipped architecture at our corpus size, identical across conditions, and
  keep the comparison — it is held constant by construction. Do not tune hparams
  per condition; that would destroy the only thing this D controls.
- **Trained and proxy disagree in direction.** That is D009's FALSIFIED branch and
  the most consequential outcome available. Report it as such, at full strength,
  and do not soften it by leaning on the metrics where they agree.
- **Cost guardrail:** stop and report past 2 GPU-hours for the closed grid (~5×
  the projection).

## Verification

- Chance is 1/37 = 0.027; every trained condition must clear it by a wide margin.
- The hparams hash is identical across all 160 runs (asserted, not assumed).
- Trace assembly reproduces the shipped loader (F5's check, re-run once at S0).
- `S_test` is loaded exactly once per run and never used for selection or stopping.
- Sums: 2,775 = 37×75, 925 = 37×25, 65 near-relative pairs, 666 = C(37,2).
- Re-running with the same seeds reproduces every metric bit-for-bit.
