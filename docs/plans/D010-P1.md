## Part 0 — S1's pilot: the statistic is not degenerate, and the exact search is cheap

### Degeneracy check — PASSED at every `k`

Real model pairs vs the same-model null (one model's 75 build configs split in
half, the self-pair control used since D007/S2a), near-relative pairs
deliberately over-sampled because those are where signal would be lost first:

| `k` | real median (hard pairs) | null p95 | ratio | **AUROC real vs null** |
|---:|---|---|---|---|
| 1 | 0.2620 (0.2503) | 0.0878 | 2.98 | **0.9850** |
| 2 | 0.3401 (0.2971) | 0.0663 | **5.13** | **0.9992** |
| 4 | 0.3475 (0.3145) | 0.0685 | 5.07 | **0.9917** |
| 8 | 0.2619 (0.2457) | 0.0683 | 3.84 | **0.9921** |
| 16 | 0.2234 (0.1986) | 0.0648 | 3.45 | **0.9900** |

**The statistic never stops discriminating.** AUROC stays ≥0.985 through 8192-d
(`k=8`) and 16384-d (`k=16`) joint vectors estimated from 75 configs. The
separation *ratio* does decline after `k=2`, so the statistic gets **weaker with
`k`, not degenerate** — which is the distinction the pilot's own pass criterion
was written to make. **D010's INCONCLUSIVE branch does not apply; S2–S6 can
proceed.**

### Cost — the exact search is affordable, so Call 2's approximation is unnecessary

Squared Euclidean distance in the concatenated space decomposes additively over
queries. Energy distance needs the *un*-squared distance, so the sum must happen
before the square root — but that is still an accumulator: adding a candidate
query to the running per-pair sums costs one add, one sqrt, one mean.

| | per cell | one greedy step (259 × 666) |
|---|---:|---:|
| naive recompute | 26.201 ms | **1.26 core-h** |
| **accumulator** | **0.051 ms** | **0.02 core-h** |
| speed-up | **519×** | |

**Full `k=8` greedy: 0.02 core-hours. Precompute: 0.01 core-h, 3.9 GB resident.**
The accumulator agrees with direct computation to **7.09e-06** absolute — it is
an optimisation, so the pilot verified it rather than assuming it.

## Call 1 (design side) — which two-sample statistic

**Proposal: energy distance, scale-free variant — the project's established
default.**

- **Comparability.** Every selection number since D007 is an energy distance;
  D008's chains, which this D's condition is compared against, were selected on
  one. Changing the statistic *and* the aggregation at once would confound the
  two, and the aggregation is what D010 is actually testing.
- **MMD would need its bandwidth re-chosen per `k`.** The concatenated space's
  scale grows with `k`, so a single global `σ²` (D008/F2's fix for exactly this
  problem) cannot hold across set sizes, and a per-`k` bandwidth reintroduces the
  cross-`k` incomparability D007/F3 established is invalid. Energy's scale-free
  form divides by the pooled within-cloud distance and handles this by
  construction.
- MMD does decompose too (`exp(-Σ_q d²_q/σ²) = Π_q exp(-d²_q/σ²)`), so it is
  equally cheap — the objection is the bandwidth, not the cost. **Offered as a
  secondary robustness check at `k=8` only** if design side wants one; it is
  minutes, not hours.

## Call 2 (design side) — is a cheaper approximation needed?

**Proposal: no. Run the exact greedy.** D010 asked for an approximation *if the
naive version is too slow*; the accumulator makes the exact search 519× cheaper
than naive and the whole `k=1..8` chain costs 0.02 core-hours. There is no
accuracy/cost trade-off to make, which is the best possible answer to this Call.

## F1 — A pre-registered prediction, recorded before the chain exists

The pilot's separation ratio **peaks at `k=2` (5.13) and declines to 3.45 by
`k=16`**. Read against D009/R2's hypothesis, that is two things at once: joint
information *adds* something at small `k` (the ratio rises from 2.98 to 5.13 when
the second query joins), and dimension starts charging for it after that.

**Prediction, registered now:** if the interaction-blindness hypothesis is right,
the joint-selected chain should beat CVaR-coverage **most at small `k` (1–3) and
converge by `k=8`**. If instead the advantage appears only at `k=8`, the
hypothesis is not what produced it and `R` must say so.

This project's record on pre-registration is mixed in a useful way — D006/R11's
ChatQA prediction held, D007/F2's prediction was wrong and was reported as wrong.
Recording this one the same way.

## F2 — The greedy's objective is not monotone in `k`, unlike `GreedyCover`'s

Under I4, `cov(p) = max_q S[q][p]` can only rise as queries are added, so
`GreedyCover`'s chain improves monotonically and `k=8` is always its best set.
**The joint statistic has no such guarantee**: adding a query adds 1024
dimensions, and the pilot shows the statistic can fall (the `k=2`→`k=16` decline).
So the greedy may reach a set whose every extension is worse.

**Consequences, handled rather than discovered later:**
- the per-step objective trace is recorded, and any decrease is reported, not
  smoothed over;
- the chain is still built nested to `k=8` so it is comparable with D008/D009 at
  every `k`, but `R` will state which `k` the objective actually peaked at;
- if the objective peaks well before `k=8`, that is a finding about the statistic,
  not a bug in the search.

## F3 — The null is measured at half the sample size, which makes it conservative

The self-pair null splits 75 configs into 37/37, while the real statistic uses
75 vs 75. Same n-mismatch D008/S7 documented. The null value of scale-free energy
shrinks with n, so a null measured at n=37 **over**-states the noise floor and the
separation ratios above are, if anything, understated. Stated so the ratios are
not read as exact.

## Steps

**S1 — done** (job 988957, `results/D010/degeneracy_pilot.json`).

**S2 — `LLMmap/joint_statistic.py`.** The set-level scale-free energy distance,
both the direct form and the accumulator form, with the equivalence asserted in
code (the pilot measured 7.09e-06; the assertion makes it a standing check).

**S3 — `LLMmap/joint_greedy.py`.** Greedy over the 259-query pool: at each step,
for every remaining candidate, the joint statistic of `current ∪ {q}` for all 666
pairs via the accumulator, scored by `CVaR_γ` over pairs with **γ = 0.1**, the
project default and the value D008's `cvar_max` condition used — so the new
condition differs from `cvar_max` in *aggregation only*, which is the comparison
D010 wants. Deterministic tie-break on lowest index; per-step objective trace
recorded (F2).

**S4 — the nested `k=1..8` chain** → `results/D010/selection.json`, with the
objective trace, the queries' text, and the frozen inputs' shas.

**S5 — Evaluate through D009's exact protocol.** Same `hparams` (hash asserted
equal to D009's `0ce04efbd56c…`), same I2 split, same `LLMmap/trainer.py`, same

minutes** at D009's measured 8.7 s/run. Reuses `experiments/d009_lib.py` and the

## Failure handling

- **The objective declines from `k=1`** (no set ever beats the best single
  query): report it — it would mean the joint statistic finds no interaction at
  all on this pool, which is a clean FALSIFIED with a clear mechanism.
- **A training run diverges:** D009's S4 gate applies unchanged; re-run that
  seed, and if it recurs report training instability rather than a condition
  difference.
- **Delta smaller than the 5-seed range:** reported as *not resolved*, the same
  pre-registered rule D009/F1 used and that flagged 2 of its 8 `k` values.
- **Memory:** `XY2` is 3.9 GB resident; if a node cannot hold it, process pairs
  in blocks — the accumulator is per-pair, so blocking is exact, not approximate.
- **Cost guardrail:** stop and report past 1 core-hour for selection (50× the
  measurement) or 30 minutes for the training grid.
