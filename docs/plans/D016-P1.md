## Call 1 — measured, and it collapses

D016 asks design side to choose between a reduced-seed analysis, a subsampled pair
set, or a full retrain, on the assumption that retraining is *"a materially
different cost"* and changes the D's cost *"by an order of magnitude."*

**Measured** (job 1018750 — one run, `paper8` `k`=8 **seed 1**, a seed with *no*
checkpoint):

| | |
|---|---|
| retrain wall | **9.8 s** |
| stored `mean_top1` | 0.838919 |
| retrained `mean_top1` | **0.838919** |
| \|difference\| | **0.000000** |
| **deterministic** | **yes, bit-exact** |
| **12 missing runs** | **2.0 minutes** |

**Retraining reproduces the stored number exactly.** `pl.seed_everything(seed,
workers=True)` plus a fixed `hparams` hash plus frozen inputs makes these runs
reproducible, so a retrained seed *is* the seed D009/D010 reported — not a
resample of it. There is therefore no statistical difference between "the
checkpoints existed" and "we retrain them", and the cost difference is **2
minutes**, not an order of magnitude.

**Proposal: retrain the 12 unsaved runs and proceed with the full 5-seed basis
D016 specifies.** This is not the "silent substitution" the D warns against — it
is raised here, measured, and shown to be exactly equivalent. I have **not** run
it; S1–S2 wait on this Call.

**Two secondary asks, both one-line:**

2. **`d009_train.py`'s `if r_ == 0` is worth changing at some point** — it is why
   this D needed a Call at all. Flagged, not edited (it is a prior D's file and

## F1 — The 4 non-structural hard pairs are all cross-family, which is worth a sentence in `R`

`DeciLM-7B ↔ Mistral-v0.1`, `Llama-2-7b-chat ↔ Mistral-v0.2`, `Phi-3-medium ↔
Mistral-v0.1` (×2) — none shares a `lineage` tag. If these survive S2, the finding
is not "the structural definition missed some near-relatives" but "difficulty is
not only a near-relative phenomenon", which is a materially different claim and
bears directly on `DECISIONS.md` D7. **Proposal: report the structural-membership
flag *and* the lineage relationship per pair in S2's table**, so the distinction is
visible without a second pass. Costs nothing — `structural_diagnostics` is already
imported.

## F2 — 666 pairs × 259 queries is 172k `two_way_correct` calls per condition; S2 does not need them

S3 took 27 s because it evaluates every query per pair. **S2 does not repeat that**:
it needs one forward pass per checkpoint (15 total) to get 37-way logits, then
restricting to two columns is pure arithmetic over a `(925, 37)` array — 666 pairs
× 15 runs of column-slicing. Estimated well under a minute. Flagged so the review
does not price S2 against S3's runtime.

## F3 — The per-pair bootstrap needs `cnt_pair` at 666 wide, which no stored artifact has

D015 reused stored `cnt_pair` (65, 25). For 666 pairs that array does not exist —
it must be rebuilt from S1's logits. **Proposal: recompute it inside S2 using
`d009_lib.logit_stats`'s own restriction logic with the wider pair list** (exactly
what D016/S2 specifies), then apply D015's paired config-bootstrap unchanged. Same
convention, wider input, no new statistic.
