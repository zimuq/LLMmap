## Calls

### Call 1 — F3 batching (needs design-side; departs from the D's letter)

**The D allows** a smaller F3 batch only if the corpus batch OOMs. S0 shows
two reasons to separate F3 that have nothing to do with OOM:
- **LongRoPE couples a batch.**
  - The 128k model picks short vs long RoPE factors from the **longest
    position in the batch** (`longrope_frequency_update`, `seq_len = max
    position_ids + 1`).
  - If 2k and 12k probes are batched together, the 2k probe (and the short
    F1/F2 probes, if batched with them) runs under *long* factors, a regime
    it never sees alone. That would contaminate both the 2k control and
    F1/F2.
- **Padding perturbs greedy output** (S0: about 30% of outputs change with
  batch composition).

**Options:**
- **(a) Recommended.**
  - F1+F2: one call of 14 per config, i.e. the harness at batch 64, unchanged.
  - F3: **three calls per config, one per L, each holding that L's two needle
    probes** (batch 2).
  - The two needles at a given L have **identical token length in every
    config** (2,031 bare, same wrapper), so the batch has zero padding and one
    RoPE regime. Asserted per call; batch 1 is the fallback if lengths ever
    differ.
  - 750 F3 calls per twin.
- **(b)** F3 at batch 1 (1,500 calls per twin). Identical in principle to
  (a), and about 2× the F3 cost.
- **(c)** All 20 in one batch (the D's literal default). **Not
  recommended**: it mixes RoPE regimes and padding of up to 11k tokens into
  F1/F2.

### Call 2 — the needle text (typo-level, per the D's own rule)

- `## D` writes `The secret word is *marmalade*.` inside Markdown, where
  `*…*` renders as italics.
- **TACC reads the asterisks as emphasis**, so the probe text is `The secret
  word is marmalade.` This is the default in `d026_lib`
  (`NEEDLE_LITERAL_ASTERISKS = False`); if design-side wants literal
  asterisks, flip that flag.
- No other probe text is affected.

### Call 3 — the 2k "control" is not a clean control (interpretation; needs design-side)

**The D's premise:**
- "The 2k probes are a within-pair control. Both models should succeed
  there. If they separate the twins at 2k, the separation is not about the
  context limit."

**S0 facts against it:**
- The 4k model's **2,047-token sliding window is live** (12.8 logit shift at
  3,000 tokens; 0.0 at 1,500).
- **114/125** wrapped 2k probes exceed 2,047 tokens. With the needle at the
  start of the user text, it is out of direct attention range for the 4k
  model's answer position in most configs.
- The 4k model can still reach it indirectly, layer to layer (40 layers ×
  2,047), so failure is not guaranteed. But "both should succeed" is no
  longer a safe premise.
- Neither twin's template has a system role. The system prompt (and any RAG
  or CoT wrapper) therefore sits *before* the needle. "The very beginning of
  this message" is literal only in the **9 plain configs per twin** (no
  system prompt, CoT or RAG).

**Options (no probe is edited in any of them):**
- **(a) Recommended.**
  - Keep 273/274 and re-label them in R as a **"window-boundary" probe, not
    a control**.
  - Report 2k results split by wrapped length: ≤ 2,047 tokens (11 configs
    per twin; too few for a resolved number, so descriptive) vs > 2,047.
  - A 2k separation is then **not** read as "not about the context limit":
    it is consistent with the sliding window, a context-handling mechanism.
- **(b)** Design-side adds a genuine within-window control (e.g. L = 1,000,
  2 probes, ids 279/280) by amending `## D`. Cost: about 2 min of
  generation. This is a probe-list change, so it is design-side's call, not
  TACC's.
- **Related fact for the D's framing.** Every pool prompt and every F1/F2
  prompt is ≤ 1,024 tokens. So the twins' two architectural context
  differences (sliding window, LongRoPE switch) are **inert on the whole
  existing pool**, and the pool can only see the weight and fine-tune
  difference plus the 128k model's short-factor RoPE. That is a plausible
  mechanism for why no pool chain gets past ~.90 on this pair.

## Steps after approval

All steps use the frozen `corpus_v1` for pool responses (I6). Every script is
new (`experiments/d026_*.py` plus slurm files). The D006 harness is imported,
never edited.

**S1 — Generate** (`d026_s1_generate.py`, one `gh` job per twin, run in
parallel).
- **Load** through `d026_lib.load_twin`. This is the D006 code path
  (`LLM_huggingface`, bf16, `device_map=cuda`, the use_cache rule), pinned to
  the shard's recorded `hf_revision` and asserted on load. Neither twin needs
  a D006 quirk (asserted).
- **Configs:** for each of the model's 125 `(pool, config_index)` rows in
  `corpus_v1`, `PromptConf.from_dict(row["prompt_conf"])`. The written
  `prompt_conf` is asserted equal to the corpus row's.
- **Generation, per config**, through `make_dataset_entries_for_new_llm`
  (`max_new_tokens`=200):
  - F1+F2 (ids 259–272, 14 probes) as **one call at the corpus batch size
    64**, so all 14 go in one batch. That is exactly what the harness does
    with ≤ 64 queries.
  - F3 (ids 273–278) as **three calls, one per L, each with its two needle
    probes** (batch 2, zero padding asserted; batch 1 fallback), per Call 1
    option (a).
  - The two lists are concatenated into one row with 20 traces, in id order.
- **Seeds.** `torch.manual_seed(int(sha256(f"{model}|{pool}|{config_index}"))
  % 2**31)` before each config. `corpus_v1` used no seed, so this makes the
  extension reproducible without changing its distribution (greedy configs
  are unaffected).
- **Output:**
  - `data/corpus_v1_ext_d026/{slug}.jsonl` + `.status.json`, schema =
    `corpus_v1`, restartable per config, as the D006 shard is;
  - `confs/queries/pool_d026_ext.json`: ids 259–278, texts, families, F3 meta,
    sha256.
- **Validation before claiming COMPLETE:**
  - 125 configs × 20 traces;
  - empty-response *rate* reported, not zero-required (ENV.md discipline
    item 1);
  - shard sha256.
- **Embed** (`d026_embed.py`, same job, after generation): the I5 model,
  `mean_pool` imported from `d006_s6_embed`, `max_length` 512, fp16, no
  normalisation. The output index has the same row format as `corpus_v1`'s
  (`pool`, `config`, `query_index` = 0..19 ↔ id 259 + i, `empty`).
- **Embedding parity.** Re-embed 50 stored *pool* responses of each twin
  through the same function, and assert max |Δ| ≤ 1e-2 against
  `corpus_v1/embeddings` (fp16 storage). This shows the I5 path is unchanged.
- **Gitignore.** `data/corpus_v1_ext_d026/` is added to `.gitignore`, like
  `corpus_v1`. The query texts of F3 make the shard about 80 MB. A one-line
  `.gitignore` edit, disclosed.
- **Commit and push** `results/D026/extension_manifest.json` (shard and
  embedding sha256s, statuses, revisions, wall time, gen/s, empties, the
  per-model F3 output-class table) and the query file, **before any
  analysis**, as the D requires.

**S2 — Analysis** (`d026_analysis.py`, a CPU `gh` job, `llmmap-gpu` env, no
plotting; `d026_plots.py` under `llmmap` for `curves.png`, per the
env-split pitfall).

- **Data.** For each twin and split:
  - POOL cube from `d007_lib.load_corpus(pool)`, which reads
    `corpus_v1/embeddings` (tok200, unnormalised), restricted to the twins;
  - NEW cube from the extension, joined on `(pool, config_index)`.
  - S_build: 75 configs × 2 = 150 traces. S_val: 25 × 2 = 50. S_test: 25 × 2
    = 50.
  - Label 0 = 128k, 1 = 4k.
- **Classifier (fixed by the D).** `LogisticRegression(C=1.0, solver="lbfgs",
  max_iter=20000, tol=1e-6)`, deterministic.
  - Features: the concatenated response embeddings of the set, in selection
    order. No query embedding.
  - Fit on S_build only. Non-convergence (`n_iter` = `max_iter`) is counted
    and reported.
- **Selection.** Greedy forward selection, nested to `k`=8:
  - At each step, every remaining candidate q is scored by the S_val mean
    log-loss (`sklearn.metrics.log_loss`, labels [0, 1]) of the classifier
    fit on S_build with features S + [q].
  - The argmin is appended. Exact float ties go to the lowest id.
  - The same function runs for every candidate set:
    - **POOL** (259 candidates);
    - **NEW** (14 candidates; F1+F2);
    - **POOL+NEW** (273 candidates);
    - **POOL+NEW+F3** (279 candidates, secondary (c) only).
  - Selection never reads S_test.
- **Evaluation.**
  - For each set and `k`=1..8, refit on S_build and predict S_test once. Two-way
    accuracy over 50 traces (decision > 0 → 4k).
  - Per-config correct counts `c_j` ∈ {0, 1, 2} are stored.
  - S_val accuracy is stored too, for the optimism column.
- **Intervals.**
  - `M = d008_lib.boot_draws(25, 2000, seed=20261001)`, one set shared by
    every arm and `k`.
  - acc* = `M·c / (2·ΣM)`.
  - Δ* is the paired difference within each draw; CI = 2.5/97.5 percentiles.
- **Primary label.**
  - `acc_test(POOL, 4)`, `acc_test(POOL+NEW, 4)` and Δ with its CI.
  - Labels are checked in the D's order: CEILING (> 0.95), GO, NO-GO,
    INCONCLUSIVE, with M = 0.05.
  - **If POOL+NEW selects no new probe within its first 4, its 4-set equals
    POOL's, so Δ ≡ 0 for every draw and the label is NO-GO.** That is the
    correct reading (the new probes were not preferred on S_val), and R will
    say so explicitly.
- **Secondaries:**
  - **(a) NEW vs POOL, `k`=1..8.** Point estimates, CIs, and Δ(NEW − POOL).
  - **(b) Per-probe table** for all 20 new probes:
    - single-query S_val log-loss and accuracy, and S_test accuracy;
    - byte-identical between twins on the greedy reference configs (128k
      config 22 vs 4k config 56, both tier 1, identical `prompt_conf`; the
      pool count, 46/259, is reproduced in this P);
    - for the selected sets, S_val − S_test accuracy (optimism), `k`=1..8.
  - **(c) F3, deployment-dependent, never pooled:**
    - per-probe single-query accuracy at each L, with the 2k rows first;
    - POOL+NEW+F3 vs POOL+NEW at `k`=4, Δ with its CI;
    - **output classes** per model × probe × split, by a fixed rule:
      - RETRIEVED: the needle word is in the response, case-insensitive;
      - DEGENERATE: otherwise, if the response is empty, *or* its unique
        word-3-gram ratio < 0.5, *or* > 30% of its characters are non-ASCII;
      - WRONG: everything else.
    - The rule is descriptive only. Its thresholds are fixed here, before
      any output is seen.
  - **(d) Reference rows.**
    - D025 GLOBAL `k`=8 `[193, 140, 237, 114, 233, 117, 0, 16]` and FAM:Phi
      `k`=8 `[9, 140, 65, 145, 18, 56, 44, 131]`
      (`results/D025/selection.json`), each fit as above.
    - S_test accuracy with CIs, in their own slot order.
    - Also at `k`=4 (first 4), to sit next to the primary.
  - **(e) Hand inspection.**
    - The 3 new short probes with the lowest single-query S_val log-loss
      (ties: higher S_val accuracy, then lower id).
    - For each, quote both twins' responses on 3 configs: the greedy
      reference (22 / 56) and that model's two lowest-index sampled S_build
      configs.
    - State whether the separation is semantic (e.g. a different stated
      context length) or stylistic or artefactual.
    - The same is done for the best F3 probe, separately.
  - **(f) Linear meanpool, C=3.0** (D017). The whole procedure is repeated:
    selection *and* evaluation use the meanpool classifier. Primary Δ at
    `k`=4 with its CI and the label, as a readout-sensitivity row.
- **Mandatory tail check (CLAUDE.md).** This D builds no separability tensor
  and the primary is a single pair, so the hard-tail plot has no object.
  R states this explicitly rather than skipping it silently.
- → `results/D026/analysis.json`, `results/D026/curves.png` (POOL / NEW /
  POOL+NEW, `k`=1..8, CI bands; the meanpool panel beside it).

**S3 — `## R`.**
- Label first, then curves, the per-probe table, F3 (2k first), the
  reference rows, hand inspection, and the measured cost (`sacct`).
- Commit and push.
