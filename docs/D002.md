## D — The question

> **Is Vista's GPU inaccessibility a fixable configuration/partition issue or a
> genuine platform limitation — and, once resolved either way, what does Phase 1's
> corpus construction actually cost in GPU-hours and wall-clock, measured rather
> than estimated?**

Two sub-questions, both required:

1. Is `torch 2.7.1+cpu` + no GRES on `gh`/`gh-dev` (D001/P1 §F5) a wrong
   partition/wrong-build problem, or is GPU genuinely unavailable to this
   workload on Vista?
2. Given real throughput, what will ~10⁵-generation-scale corpus construction
   actually cost, across a few candidate `(|L|, |Q_0|)` combinations?

### Why this gates everything

Phase 1 cannot be responsibly scheduled on a guess. If GPU access is fixable,
we need the real throughput number to size `A1`/`C3` correctly. If it is not
fixable, `A1`/`C3` must shrink to fit CPU throughput, or the corpus-building
strategy changes shape entirely (e.g. splitting work across a hosted inference
API for part of the universe). Discovering either of these mid-run wastes a
queue cycle.

---

## What counts as an answer

| Outcome | Criterion |
|---|---|
| **GPU_AVAILABLE** | A correct partition/QoS/build was found; measured throughput under real GPU scheduling; extrapolated cost table produced. |
| **GPU_UNAVAILABLE** | Genuine platform limitation confirmed (not a config mistake); CPU throughput measured instead; extrapolated cost table under CPU-only; explicit recommendation on how `A1`/`C3` must shrink to fit. |
| **PARTIAL** | Some partitions/nodes expose GPU, others don't. Report per-partition, recommend which to target. |

---

## Required measurements

**M1 — Locate a partition that actually exposes GPU to Slurm.** Check whether
`gh`/`gh-dev`'s missing GRES is a config issue specific to those partitions
(wrong flags, wrong QoS) before concluding the platform lacks GPU access. Check
other Vista partitions if applicable.

**M2 — Confirm the accelerator is actually used, not silently falling back to
CPU.** Install an aarch64 CUDA-enabled torch build if needed. Verify with a
trivial on-device op — don't infer this from `pip list`.

**M3 — Small real benchmark.** 2–3 models spanning the size range we're likely
to use (e.g. a ~3B and a ~8–9B) × the paper's existing 8 queries (a stand-in,
not the real pool) × a handful of configs. Measure tokens/sec, wall-clock per
model, memory footprint.

**M4 — Extrapolate to Phase-1 scale using M3's *measured* throughput.** Report
as a table across a few candidate `(|L|, |Q_0|)` pairs (e.g. 20×80, 25×100,
30×120) so `A1`/`C3` can be chosen against a real cost curve, not a single
point estimate.

**M5 — If GPU remains unavailable after M1/M2:** measure CPU throughput at the
same scale as M3, and produce the same extrapolation table under that regime.

---

## Constraints

**Applicable invariants:** none of I1–I7 bind directly — this is infrastructure,
not method.

**Out of scope:** do not build the real corpus, do not generate the actual
`Q_0` pool. This is a feasibility/costing measurement only. Reuse the paper's 8
queries and a small model subset as stand-ins — nothing here should be treated
as part of Phase 1 itself.

**Keep this D's own cost small.** It exists to avoid misallocating a much larger
budget, not to become a large job itself — a few GPU-hours or less, total.

**Code-change rule (per `CLAUDE.md`).** `gate: REVIEW` is set here specifically
because any nontrivial environment fix (e.g. installing a different torch
build) should be disclosed as part of P and reviewed, not committed ahead of
approval — unlike the two pre-existing aarch64 fixes from before D001, which
predated being handed any D.

### P1

**Status: PROPOSED — awaiting review.** Full plan: [`plans/D002-P1.md`](plans/D002-P1.md).
Recon below is read-only — per this D's code-change rule, nothing was installed or
modified.

**Headline: D001/P1 §F5 was wrong, and it is the substance of M1.** The missing GRES
is not a misconfiguration and not a platform limitation — it is Vista's documented
design. Each GH node has **one NVIDIA H200, 96 GB HBM3**, and the TACC user guide
states Vista **does not support `--gres` / `--gpus-per-task`; Slurm rejects any job
script containing them.** GH nodes are exclusive, so the GPU is simply present.

> The only real cause of D001 running on CPU was the CPU-only wheel
> (`torch 2.7.1+cpu`) installed during environment bring-up. D001's numbers are
> unaffected (small job either way), but the Review's "GPU access appears broken"
> follow-up overstates the problem. Expected verdict: **GPU_AVAILABLE** — which is
> precisely why M2's on-device check, not a docs citation, decides it.

**Partitions.** `gh` (576) and `gh-dev` (20) — 72 cores + 1× H200. `gg` (251) —
144 cores, **CPU-only by design** (targeting it would reproduce the "no GPU"
symptom legitimately). `gb` (18) — Grace-Blackwell, absent from the user guide.
CUDA modules 11.8–12.8 exist; no PyTorch module; `tacc-apptainer` as container
fallback.

**Second finding, likely dominating the cost answer.**
`make_dataset_entries_for_new_llm` (`LLMmap/dataset_maker.py:36-39`) generates
**one prompt at a time**, although `LLM_huggingface.generate` already supports
batched input (`llm.py:74-89`). Batch-1 decoding leaves most of an H200 idle, so M3
measures **both** unbatched and batch-8 (the 8 queries within one config — same
sampling params, so it is valid). That ratio plausibly decides Phase-1
affordability. This plan only *measures* it; changing `dataset_maker.py` belongs to
the Phase-1 D.

**Steps.** S0 prereqs — a **separate `llmmap-gpu` env** (the `llmmap` env is left
untouched so D001 stays reproducible) + CUDA aarch64 wheel + login-node weight
pre-staging (compute-node egress untested) · S1 M1/M2 on-device verification
(`nvidia-smi`, real matmul, `memory_allocated`, CPU cross-check — never inferred
from `pip list`) · S2 M3 benchmark on `Qwen2.5-3B-Instruct` and
`Qwen2.5-7B-Instruct` (**ungated**, both already in D001's universe) × the paper's
8 queries × 10 configs, both regimes · S3 M4 extrapolation over
`(|L|,|Q_0|) ∈ {20×80, 25×100, 30×120}` · S4 CPU fallback only if S1 fails · S5
write R.

**Cost.** One `gh-dev` job, `-t 01:00:00`; **≤1 GPU-hour**, inside this D's "a few
GPU-hours or less" limit. Also reports a **storage** line for M4: ~25 models ≤14B
is ~300–400 GB of weights against ~850 GB free on `$WORK` — feasible, but a real
A1 constraint.

**Needs the human:** `HUGGINGFACE_API_KEY` must be exported —
`LLM_huggingface.__init__` raises without it (`llm.py:23-25`), even for ungated
repos. This is the only blocking external input; ungated models avoid the separate
license-acceptance issue.

### Technical log (for TACC / audit trail — skip unless "For you" told you to)

**Why this is a clean approve.** The plan does what D002 asked and nothing
more: it establishes GPU availability empirically (F1's "expected
GPU_AVAILABLE" claim is explicitly left to S1's on-device check, not assumed
from the Vista docs citation — correct, since M2's whole point is "don't
infer from `pip list`"), and it caps its own cost inside D002's "a few
GPU-hours or less" budget (≤1 GPU-hour, one `gh-dev` job).

**Code-change rule compliance.** §0 states explicitly that recon was
read-only and nothing was installed. §S0 discloses every environment change
up front: a *separate* `llmmap-gpu` conda env (existing `llmmap` env
untouched, preserving D001 reproducibility), a CUDA aarch64 torch wheel, and
login-node weight pre-staging. This is exactly the disclosure D002's gate
exists to require — nothing here should be committed or installed ahead of
this approval, and none of it was.

**F1's correction to D001's Review.** D001-Review-P1-v2.md's follow-up said
"GPU access appears broken." P1's recon (Vista's user guide: GH nodes don't
support `--gres`/`--gpus-per-task` at all; GPU is simply present on every
exclusive GH node allocation) shows that framing overstated the problem —
the actual cause was a CPU-only torch wheel, not missing GPU access. This is
correctly caught and will close the record accurately once S1 confirms it
empirically. No action needed from the human; noting it here so the D001
Review's follow-up #1 isn't left dangling in two different states across two
files.

**Scope discipline.** Out-of-scope items (no real corpus, no `Q_0`
generation, no `dataset_maker.py` batching fix) are all respected — F5's
batch-1-vs-batch-8 throughput gap is *measured*, not fixed, with the actual
fix explicitly deferred to the Phase-1 D. That is the right call: fixing it
now would conflate an infrastructure D with a method-affecting code change
outside this D's REVIEW scope.

**Cost model (§S3) is stated explicitly** rather than baked into a single
number, so design-side or a future reader can substitute different `C4`
(config-split) assumptions once that decision is actually made — appropriate
given `n_configs=125` is flagged inline as itself undecided.

**Nothing found that needs an amendment.** Failure-handling table (§3) covers
the realistic failure modes (Slurm GPU-flag rejection, `cuda.is_available()`
False, wheel install failure, no egress, missing token, OOM) with reasonable
responses; verification checks (§4) include a CPU-vs-GPU numerical agreement
check, which is the right guard against "ran on GPU but the math is wrong."
