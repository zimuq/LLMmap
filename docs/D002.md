## D — The question

> **Is Vista's GPU inaccessibility a fixable configuration/partition issue or a
> genuine platform limitation — and, once resolved either way, what does Phase 1's
> corpus construction actually cost in GPU-hours and wall-clock, measured rather
> than estimated?**

Two sub-questions, both required:

1. Is `torch 2.7.1+cpu` + no GRES on `gh`/`gh-dev` (D001/P1 §F5) a wrong
   partition/wrong-build problem, or is GPU genuinely unavailable to this
   workload on Vista?
2. Given real throughput, what will ~10⁵-generation-scale corpus construction
   actually cost, across a few candidate `(|L|, |Q_0|)` combinations?

### Why this gates everything

Phase 1 cannot be responsibly scheduled on a guess. If GPU access is fixable,
we need the real throughput number to size `A1`/`C3` correctly. If it is not
fixable, `A1`/`C3` must shrink to fit CPU throughput, or the corpus-building
strategy changes shape entirely (e.g. splitting work across a hosted inference
API for part of the universe). Discovering either of these mid-run wastes a
queue cycle.

---

## What counts as an answer

| Outcome | Criterion |
|---|---|
| **GPU_AVAILABLE** | A correct partition/QoS/build was found; measured throughput under real GPU scheduling; extrapolated cost table produced. |
| **GPU_UNAVAILABLE** | Genuine platform limitation confirmed (not a config mistake); CPU throughput measured instead; extrapolated cost table under CPU-only; explicit recommendation on how `A1`/`C3` must shrink to fit. |
| **PARTIAL** | Some partitions/nodes expose GPU, others don't. Report per-partition, recommend which to target. |

---

## Required measurements

**M1 — Locate a partition that actually exposes GPU to Slurm.** Check whether
`gh`/`gh-dev`'s missing GRES is a config issue specific to those partitions
(wrong flags, wrong QoS) before concluding the platform lacks GPU access. Check
other Vista partitions if applicable.

**M2 — Confirm the accelerator is actually used, not silently falling back to
CPU.** Install an aarch64 CUDA-enabled torch build if needed. Verify with a
trivial on-device op — don't infer this from `pip list`.

**M3 — Small real benchmark.** 2–3 models spanning the size range we're likely
to use (e.g. a ~3B and a ~8–9B) × the paper's existing 8 queries (a stand-in,
not the real pool) × a handful of configs. Measure tokens/sec, wall-clock per
model, memory footprint.

**M4 — Extrapolate to Phase-1 scale using M3's *measured* throughput.** Report
as a table across a few candidate `(|L|, |Q_0|)` pairs (e.g. 20×80, 25×100,
30×120) so `A1`/`C3` can be chosen against a real cost curve, not a single
point estimate.

**M5 — If GPU remains unavailable after M1/M2:** measure CPU throughput at the
same scale as M3, and produce the same extrapolation table under that regime.

### P1.a — amendment (post-approval, human-directed 2026-09-01)

Disclosed per the code-change rule. **Model weights move from `$WORK` to
`$SCRATCH`.** P1 as approved staged them under `$WORK/vista/.cache/huggingface`.

Rationale (Vista file-system table): `$SCRATCH` has **no quota** (~10 PB); `$WORK`
is capped at **1 TB shared across all TACC systems** and is the scarce resource.
Model weights are freely re-downloadable and should not consume it — `$WORK` should
hold experiment data (corpora, tensors, results).

**Consequences for M4's cost answer:**
- Storage stops being a binding constraint. ~300–400 GB for a ≤14B universe is
  free on `$SCRATCH`, and **adding a 70B-class pair (~260 GB more) is affordable on
  storage grounds** — directly relevant to D001 §R4, which found a strict ≤14B
  universe excludes D001's own motivating case (Llama-3-70B ↔ Smaug-70B).
- A **new** constraint replaces it: `$SCRATCH` is **purged after 10 days without
  access**, and access time updates on compute-node use, not login-node reads. Any
  Phase-1 build spanning more than 10 days must touch the weights or budget
  re-download. This will be reported in R alongside GPU-hours.

No measurement is affected; this is purely a storage path. The frozen
`multilingual-e5-large-instruct` cache (~1.1 GB, I5) stays in `$WORK` so D001/D004
reuse is undisturbed.

### R1 — M1/M2: GPU is available, and D001/P1 §F5's framing was wrong

```
device: NVIDIA GH200 120GB   capability 9.0   95.0 GB visible to torch
driver 590.48.01             torch 2.7.1+cu128 (CUDA build 12.8)
on-device op: tensor on cuda:0, +80 MB allocated, matches CPU reference
```

Confirmed empirically, per M2's requirement. **The missing GRES was never the
problem** — Vista documents that `--gres`/`--gpus-per-task` are unsupported and
Slurm rejects them; GH nodes are exclusive so the GPU is simply present. The sole
cause of D001 running on CPU was the CPU-only wheel installed at bring-up. **D001's
Review follow-up #1 ("GPU access appears broken … blocks the next phase") is closed:
it does not block anything.**

**Exact steps, since D002 asked for them — two traps that both fail silently with
exit code 0:**

1. **`cu126` is the wrong index for this pin.** It publishes no aarch64 build for
   2.7.1 (it goes 2.6.0 → 2.9.0), so pip resolves 2.14.0+cu126 and then
   `requirements.txt`'s `torch==2.7.1` **downgrades it back to the CPU wheel**.
   `cu128` publishes exactly `2.7.1+cu128`.
2. **`pip install torch==2.7.1 --index-url .../cu128` is a no-op** when `2.7.1+cpu`
   is installed: PEP 440 treats `2.7.1+cpu` as satisfying `==2.7.1`, so pip prints
   "already satisfied" and exits 0. **The local version must be explicit:**
   `pip install "torch==2.7.1+cu128" --index-url https://download.pytorch.org/whl/cu128`.

The pinned version never had to change — only the CUDA variant — so nothing about
D001's reproducibility is perturbed. Scripts: `experiments/d002_s0_setup_env.sh`.

### R2 — M3: measured throughput (8 queries x 10 configs = 80 generations per cell)

| model | regime | tok | wall s | gen/s | tok/s | peak GPU |
|---|---|---|---|---|---|---|
| Qwen2.5-3B | unbatched | 100 | 220.9 | 0.362 | 32.7 | 12.7 GB |
| Qwen2.5-3B | **batched** | 100 | **35.5** | **2.255** | 201.0 | 12.7 GB |
| Qwen2.5-7B | unbatched | 100 | 169.4 | 0.472 | 38.9 | 28.6 GB |
| Qwen2.5-7B | **batched** | 100 | **32.3** | **2.478** | 207.3 | 30.0 GB |
| Qwen2.5-3B | unbatched | 200 | 344.2 | 0.232 | 30.9 | 12.7 GB |
| Qwen2.5-3B | **batched** | 200 | **64.2** | **1.246** | 159.7 | 12.7 GB |
| Qwen2.5-7B | unbatched | 200 | 235.5 | 0.340 | 40.8 | 28.6 GB |
| Qwen2.5-7B | **batched** | 200 | **53.1** | **1.506** | 179.2 | 30.0 GB |

**Batching (8 queries of one config, identical sampling params) gives 3.7-6.9x.**
Zero failed configs. This confirms P1 §F5: `dataset_maker.py:36-39`'s batch-1 loop
leaves most of an H200 idle.

**Throughput does not track parameter count.** The 7B is *faster* than the 3B
unbatched (0.472 vs 0.362 gen/s). Cause, verified from the configs: **Qwen2.5-3B has
36 layers, Qwen2.5-7B has 28**. At batch 1 decoding is launch-latency-bound, so
sequential depth dominates FLOPs. **Consequence for costing: size-based scaling laws
are invalid here** — the table below therefore uses the two measured models as a
bracket rather than a fitted curve.

### R3 — M4: SUs are not the constraint; wall-clock is

Charge rate `gh` = **1 SU per node-hour** (min 15 min/job); balance **6982 SU**.
Cost model `generations = |L| x |Q_0| x n_configs`, `n_configs = 125` (C4, itself
undecided). Full table: `results/D002/cost_extrapolation.csv`.

| \|L\|x\|Q0\| | regime | tok | generations | node-hours | % of balance | days |
|---|---|---|---|---|---|---|
| 20x80 | batched | 100 | 200,000 | 22.6–24.8 | 0.4% | 1.0 |
| 25x100 | **batched** | **100** | **312,500** | **35.2–38.7** | **0.6%** | **1.6** |
| 25x100 | batched | 200 | 312,500 | 57.8–69.9 | 1.0% | 2.9 |
| 25x100 | unbatched | 100 | 312,500 | 184.1–240.0 | 3.4% | 10.0 |
| 25x100 | unbatched | 200 | 312,500 | 255.5–374.4 | 5.4% | 15.6 |
| 30x120 | batched | 200 | 450,000 | 83.3–100.6 | 1.4% | 4.2 |
| 30x120 | unbatched | 200 | 450,000 | 367.9–539.0 | **7.7%** | 22.5 |

**Even the worst cell costs 7.7% of the balance.** The allocation does not bind at
any candidate size — which reframes D002's premise: the question was never "can we
afford it in SUs".

**What does bind is wall-clock, and it interacts with the `$SCRATCH` 10-day purge
(P1.a).** Unbatched 25x100 takes 10–15.6 days, i.e. **longer than the purge window**,
so weights would be deleted mid-build. Batched keeps every candidate ≤4.2 days,
comfortably inside it. **Batching is therefore not merely an optimization — it is
what keeps Phase 1 inside the storage window**, on top of the 3.7–6.9x saving.

### R4 — Recommendation for A1 / C3

- **C3: `|Q_0| ~100` is not cost-constrained.** Even 30x120 batched is 1.4% of
  balance. Choose C3 on methodological grounds (pool diversity, per D003), not cost.
- **A1: 25 models ≤14B is comfortably affordable** — 0.6% of balance, ~1.6 days
  batched at 100 tokens.
- **C7 is currently inert and cheap to fix.** Measured response lengths in the
  shipped corpus: mean 352, median 397, p99 584, max 667 chars — **0.0% reach 650**.
  The binding cap is `max_new_tokens=100` (`llm.py:9`), not C7's 650 chars. Raising
  to 200 tokens costs ~1.8x (25x100 batched: 1.6 → 2.9 days, 0.6% → 1.0% of balance).
  **Affordable; decide C7 on information grounds, not cost.**
- **Batch the generation loop before Phase 1.** Fixing `dataset_maker.py:36-39` is
  the single highest-leverage change available and is prerequisite to staying inside
  the purge window. Deliberately not done here (out of D002's scope); belongs to the
  Phase-1 D.

### R5 — Something D002 did not anticipate: the 70B pair does not fit

D001 §R4 recommended adding one 70B-class pair (Llama-3-70B + Smaug-70B) to retain
D001's own motivating case, "if D002's measured budget allows". Reporting per the
standing rule rather than silently absorbing it:

**It is not a budget problem — it is a memory problem.** 70B at bf16 is ~140 GB of
weights against **95 GB visible on a GH200**. It does not fit. The options each carry
a cost this D cannot decide:

- **Quantize (8-bit ~70 GB, 4-bit ~35 GB).** Fits, but quantization perturbs output
  distributions — and this project *fingerprints output distributions*. A quantized
  Llama-3-70B is arguably a different behavioural entity from the one D001 measured,
  which risks a confound in the very signal under study. **This is a methodological
  decision for design side, not an infrastructure one.**
- **CPU/unified-memory offload** via `device_map="auto"` onto Grace's 120 GB LPDDR:
  works, but is drastically slower and would need its own measurement.
- **Multi-node sharding:** more engineering, and unmeasured here.

Recommend design side treat "include a 70B pair" as an open A1 sub-decision with
this constraint attached, rather than assuming D001 §R4's suggestion is free.

### R6 — Limits of this measurement

- Only **3B and 7B** were benchmarked. The ≤14B universe extends to 14B, unmeasured;
  given R2's depth-over-size finding, do not interpolate. A 14B would need ~60 GB
  peak by naive scaling from the 7B's 30 GB — still inside 95 GB.
- Batch-8 was chosen because it is the *safe* batch (identical sampling params within
  one config). At ~200 tok/s the H200 is still far from saturated; batching across
  configs that share sampling params would likely go substantially faster. **The
  table is therefore a conservative upper bound on cost.**
- Prompt configs were drawn with `PromptConfFactory.sample()`, which is affected by
  the pool bug reported in D001's `## Review`. Irrelevant to throughput (any
  representative configs suffice) but noted so the number is not later mistaken for
  a clean-holdout measurement.
- Egress from the **login node** is fast (20 GB staged in ~25 s). Compute-node egress
  remains untested — S0.3 pre-staging made it unnecessary.
