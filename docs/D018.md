## D — The question

> **Run Algorithm H.1's actual selection procedure — `f ← train(Q,
> T_train); A ← eval(f, T_val); q* ← argmax A`, greedily, one query at a
> time — on our own 259-query pool, our own frozen corpus, `k`=1..8, using
> both the attention network and the linear classifier as the trained
> model `f`. Compare the resulting chains' final `S_test` accuracy,
> matched `k`, against our own already-selected `GreedyCover` and
> `JointGreedy` chains.**

This is the only experiment that can support "our selection algorithm
beats the paper's selection algorithm" as a true head-to-head claim.
Every comparison in this project so far (D009, D010, D015–D017) has been
against `paper8` — Algorithm H.1's published *output*, selected on a
*different* pool and corpus. Beating `paper8` is evidence for CDQD's cost
thesis (D5 claim 2, cost-asymmetric); it is not evidence that our
algorithm outperforms theirs, because the comparison has never held the
candidate pool fixed. This D holds it fixed.

### Why now, and why this is not the "expectation baseline" `METHOD.md §6.5` already rejected

`METHOD.md §6.5` rejects building a *distance-function-based
reconstruction* of Algorithm H.1 (inventing weights and a proxy statistic
to approximate what it "would" pick) as an unfounded strawman — its
resolution was `GreedyCover(γ=1.0)` as the closest defensible analogue,
**not** this D. **This D does not do that.** It runs the *actual*
procedure — real training, real held-out evaluation, greedy, one query
at a time — exactly as Algorithm H.1 is specified (`METHOD.md §2`'s own
quote of it), just on our pool instead of theirs. This is Direction B,
not the rejected §6.5 reconstruction; the two have always been distinct
in this project's own documents (`D010.md`'s header explicitly separates
them).

**Cost, already estimated, now accepted.** `PLAN.md`'s Direction B note:
"~5 GPU-hours for a full 259-query greedy search" (D009's 8.7s/run pilot
× 2,044 training runs — `259+258+…+252`, **not** the paper's own 372,
which was sized to *their* 50-query pool). The human has accepted this
cost and asked for **both classifiers**, which roughly doubles the run
count (~4,088 total) but not necessarily the wall time — the linear
classifier's own per-run cost is cheaper at small `k` and **grows with
`k`** for concatenation (D017/R4, R6: a converged `k`=8 concat fit is
32s, `k`=1 fits are much cheaper) — the *actual* total is unknown and
must be measured (S0), not assumed, following this project's standing
discipline (D002/D006/D007/D009/D010/D012/D016/D017's own precedent of a
cost pilot before committing to a full grid).

### What is and is not known going in

- **Algorithm H.1's own split is circular** — `METHOD.md §6.2`: "selects
  on `T_test` and reports on the same distribution." This project has
  twice already declined to reproduce that specific choice
  (`PAPER_DEVIATIONS.md` items 6 and 13) on direct human instruction
  ("reproducing the pipeline does not mean reproducing its unreasonable
  choices"). **This D follows the same precedent by default**: each
  greedy step's `argmax A` is evaluated on `S_val`, not `S_test`; `S_test`
  is touched exactly once, for the final chain's reported accuracy (I2).
  **Call 1, for P1:** confirm this is accepted, or state why this D
  should instead reproduce the paper's literal circular protocol (e.g.
  to isolate how much of any gap is attributable to that choice, echoing
  `TODO.md`'s parked T6.2) — not both without saying so.
- **Because the greedy step's `argmax` depends on which classifier
  produces `A`, this is two independent chains, not one chain evaluated
  twice.** The query that most improves attention-network validation
  accuracy at step `k` need not be the query that most improves the
  linear classifier's — expect the two chains to diverge, and report
  where they do (a free, informative byproduct, same spirit as D012/R4's
  and D014's chain-overlap reporting).
- **Seed policy during the search is a real cost/fidelity trade-off, not
  a detail.** Evaluating every candidate at every step with this
  project's standard 5-seed protocol would multiply the attention-side
  cost 5× (~25 GPU-hours). Algorithm H.1's own description ("372 real
  training runs") implies **one training run per candidate**, not five —
  so a single seed during the search is not just a cost compromise, it is
  arguably *more* faithful to the algorithm as specified. **Proposal:**
  one fixed seed during the greedy search itself (which candidate wins at
  each step); the standard 5-seed protocol only for the *final* selected
  `k`=1..8 chain's reported comparison (matching every other D in this
  project). **Call 2, for P1:** confirm or propose otherwise, and state
  the resulting cost either way.
- **The linear classifier's pooling choice for the search itself is
  undecided and directly affects cost.** D017 established concatenation
  as the higher-fidelity choice for the *final* headline comparison, but
  its cost scales with `k` (more features), which is exactly where this
  D spends the most candidate evaluations (steps at `k`=6–8 each try
  ~253–259 candidates at the most expensive feature size). Mean-pooling
  is `k`-cost-flat but structurally cannot distinguish which query
  produced which response (D017/R4's 3.7–7.0pp accuracy gap is the price
  of that). **Call 3, for P1, after S0's cost pilot:** run the *search*
  with mean-pooling (cheaper, matches Algorithm H.1's own presumed cost
  profile better) and report the *final* chain under both poolings for
  comparability with D017 — or run the full search under concatenation
  if S0 shows it is affordable. State the choice and the reasoning, not
  silently.

**S0 — Cost pilot, mandatory before any commitment to the full grid.**
Time a handful of real candidate evaluations at representative `k` (e.g.

(b) the linear classifier under concatenation, (c) the linear classifier

cost is a surprise** (this project's standing practice — D002, D006,
D007, D009, D010, D012, D016, D017 each did this before committing).

**S1 — Implement the greedy loop.** At step `k` (starting `k`=1), for
every remaining candidate query `q`: form the `k`-query set (current
best `k`-1 queries + `q`), train the classifier on `S_build`, evaluate
mean top-1 on `S_val` (Call 1), pick `q* = argmax`. Fix the queries chosen
at prior steps (standard forward greedy — same structure as
`GreedyCover`/`JointGreedy`, not the paper's original innovation, just
applied with a real classifier's real accuracy as the criterion instead
of a tensor statistic). Repeat to `k`=8. One seed during the search (Call
2). Produce two chains: `H1-attention`, `H1-linear` (pooling per Call 3).

**S2 — Evaluate the final nested chains properly.** For each of
`H1-attention`, `H1-linear`, at every `k`=1..8: retrain/evaluate via this
project's standard protocol — 5 seeds for the attention network (matching
D009), the linear classifier's own deterministic fit plus the config-level
paired bootstrap (matching D017) — reporting `S_test` accuracy exactly
once per chain per `k` (I2). Report all four `METHOD.md §8` metrics.

**S3 — Compare against `GreedyCover`/`JointGreedy`** at matched `k`,
reusing their already-existing numbers verbatim (D009/D010/D015's own
result files, I6) — do not rerun them.

**S4 — The hard-pair view, reusing D015's machinery unchanged.** Extend
S2's per-condition numbers to the per-pair `hard_subset` breakdown (the
65 structural pairs, same definition, same extraction code as D015) for
`H1-attention`/`H1-linear` at `k`=8 — enables a direct "does the paper's
real search algorithm find something that specifically helps the named
hard pairs" comparison, the natural extension of this session's D015–D017
line of work.

**S5 — Report chain overlap and the three-way verdict**, per "What counts
as an answer" above.

**S0 — all five arms priced.** 2,044 candidate evaluations per arm
(259+258+…+252), per-evaluation cost measured at `k` = 1/4/8 and weighted by the
real candidate count at each step:

| arm | `k`=1 | `k`=4 | `k`=8 | projected full search |
|---|---|---|---|---|
| **attention network** | 3.1 s | 5.4 s | 3.8 s | **2.47 h** |
| linear concat, tight (`20000/1e-6`) | 3.2 s | 9.2 s | 18.5 s | **5.98 h** |
| linear concat, loose (`3000/1e-4`) | 2.4 s | 4.9 s | 7.0 s | 2.79 h |
| **linear mean-pool, tight** | 4.5 s | 3.8 s | 4.0 s | **2.30 h** |
| linear mean-pool, loose | 2.9 s | 2.3 s | 2.3 s | 1.39 h |

Three results that contradict the D's expectations: **(1)** the attention network
costs 2.47 h, not ~5 h — D009's 8.7 s/run included checkpointing and full test
evaluation, which a search step needs neither of; **(2)** `k`-scaling runs in
*opposite* directions — attention is essentially `k`-flat while concat grows **6×**
from `k`=1 to `k`=8, which is why concat-tight is the most expensive option of all
five; **(3)** solver tolerance is worth 2.1× on concat.

**Call 1 — `S_val` argmax, confirmed.** Follows `PAPER_DEVIATIONS.md` 6/13 and the
human's standing instruction. **On the record before results exist:** this makes the
comparison *harder* for H.1, since its own protocol lets it select on the split it
is scored on. **A PARITY-OR-BETTER outcome is therefore "we match/beat H.1 run
under a fairer protocol than it specifies", not "H.1 as specified".** The literal
circular variant as a sensitivity arm is +2.5 h — asked, not assumed.

**Call 2 — one seed in the search, five for the final chain, as proposed.** D018's
argument is right: "372 training runs" implies one run per candidate, so this is
more faithful, not a compromise (5 seeds would make the attention arm 12.4 h).
**Stated risk:** candidate-to-candidate margins at a greedy step will often be
smaller than the attention network's own 0.024–0.081 seed range, so **the chain is
noisy — a property of Algorithm H.1 as specified, not of this implementation.** Each
step's winning margin is recorded so `R` can show it rather than assert it.

**Call 3 — mean-pool at the TIGHT solver for the linear search (2.30 h); both
poolings at final evaluation.** Concat-tight at 5.98 h is not worth 2.6× for a step
whose only output is an argmax. And **loosening the solver is the wrong lever**:
D017/Call 1 showed the loose setting produces a 0.004 wobble from non-convergence,
which is the same size as many candidate-to-candidate differences — a loose argmax
could be selecting convergence noise. Mean-pool-tight avoids both. **Fidelity cost
disclosed:** D017/R4 measured concat − mean-pool at +3.7 to +7.0 pp, so the search
is guided by a weaker readout than the one the final numbers use. That is the same
asymmetry H.1 itself has, and `R` will say so.

**F1 — the two arms answer different questions.** The attention arm *is* Algorithm
H.1. **The linear arm is not** — it is the same procedure with a classifier the
paper never used and which D017 showed is *better* at every `k`. Proposal: **the
attention arm is the head-to-head result, the linear arm a robustness check on
whether the search procedure or the classifier is doing the work** — labelled that
way, never averaged into one "H.1" verdict.

**F2 —** reuse of `GreedyCover`/`JointGreedy` gets the assertion that caught bugs in
D014 and D016: D012/D013 store runs only for γ's they trained, and the reused ones
live in D009/D010. Chains and `k`=8 metrics will be asserted against
D008/D010/D015 before any comparison.

**F3 — pre-registering the resolution problem.** PARITY-OR-BETTER is defined by TOST
at δ=0.02, which is **inside** the attention network's own 0.024–0.081 seed range.
**Proposal, fixed now:** report PARITY only when the TOST interval is within ±0.02
**and** |Δ| is below the 5-seed range; otherwise INCONCLUSIVE. Without it, "parity"
would be reported for something the instrument cannot distinguish from a loss.

**Cost:** attention 2.47 h + linear mean-pool tight 2.30 h ≈ **4.8 GPU-hours**, plus
~15 min for S2. **Nothing runs until Calls 1–3 are dispositioned.**
