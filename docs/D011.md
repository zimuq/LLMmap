## D — The question

> **Corrected 2026-09-13 (TACC_NOTES issue 13 — the original wording
> below was wrong; see the note after it).** Of the 32 pairs D008
> flagged, split-half robust (not the naive 33 — see Part 0's premise
> correction below) — where the tensor's own per-pair top-ranked query
> (chosen by build-time score) generalizes poorly to test, while a
> different pool query does much better on test for that same pair —
> does `JointGreedy`'s already-selected `k=8` chain (D010) resolve any
> of them, at D008's own accuracy scale (2-way test accuracy ≥ 0.75,
> its `T2` threshold), and via which mechanism: (a) one of its 8 chosen
> queries happens to be individually strong enough for that pair, or
> (b) the chosen set resolves it *jointly* while no single member does?

**What was wrong in the original wording, and why it doesn't change
what this D does.** The original draft described these as pairs where
*"no query in `GreedyCover`'s selected chain separates them well"* —
implying `GreedyCover`'s shared 8-query budget passed over an available
query due to opportunity cost across the 666 pairs. **That is not what
D008 computed.** `D008`'s script (`experiments/d008_frontier.py:95`,
`qstar = S.argmax(axis=0)`) takes the argmax over **all 259 pool
queries** per pair — `GreedyCover`'s chain never enters it. The real
finding is a **per-pair build→test generalization gap**: the query that
looks best on build data for a given pair doesn't reliably stay the
best on test data for that same pair — a property of the tensor's own
per-pair estimate, unrelated to which 8 queries any downstream
algorithm happens to select. TACC caught this while planning D011
(`TACC_NOTES.md` issue 13) — the root cause is in D008's own `## R`
prose, which narrated this away, and this project's own D008/D009/D010
write-ups repeated it uncritically. **This D's steps (S1–S6) do not
change** — comparing `GreedyCover`'s and `JointGreedy`'s chains against
these 32 pairs is still exactly the right thing to check; only the
*reason* they were flagged, and therefore what a "recovery" would mean,
needed correcting. (a) recovering a pair no longer means "`JointGreedy`
happened to value a query `GreedyCover`'s shared budget couldn't
afford" — it means "`JointGreedy` picked a query that generalizes to
test where the tensor's naive per-pair favorite didn't." (b) is
unchanged: the set resolves it jointly where no member does alone.

### Why this exists now

D008 and D010 are two separate, already-closed findings that had never
been directly cross-referenced — and, per the correction above, D008's
own finding had a premise issue nobody had re-checked against its actual
code. Everything needed is already computed — no new generation, no new
training, no GPU. This is the cheapest possible way to connect the two
findings, now on a corrected footing, before deciding anything about
Phase 3's future scope.

### What's already decided and does not block this D

- **No new artifacts.** `S_energy` (D007), the 32-pair list (split-half
  robust — see Part 0 below) and `GreedyCover`'s chain (D008),
  `JointGreedy`'s chain and its statistic implementation (D010) are all
  reused verbatim (I6). This D reads, it does not regenerate or retrain.
- **Stays at the tensor/statistic level, not the trained classifier.**
  D008's original finding was itself a tensor-level diagnostic (2-way
  test accuracy against a threshold, its `T2`), not a trained-classifier
  result — this D answers the same kind of question at the same level
  and on the **same scale**, for direct comparability. Whether a
  recovered pair also shows up correctly classified in D009/D010's
  *trained* per-condition results is a natural follow-up, not required
  here.
- **Premise, corrected before this D runs (Part 0, TACC's own check):**
  D008's naive "33/37 at oracle ≥0.95" figure selects the best query on
  the same split it then scores — a winner's-curse inflation
  (~7 accuracy points), the same class of error D007/F2 already caught
  once. **Split-half robust, the count is 32/37, mean 0.970** (vs. the
  naive 33/37, mean 0.977) — the qualitative claim survives, the exact
  number and its optimism do not. This D works from **32**, not 33.

## What counts as an answer

**Pre-registered, not just "non-trivial" (per Call/F4):** count pairs
where `JointGreedy` clears D008's own `T2` threshold (2-way test
accuracy ≥ 0.75, same classifier/split as the original flag) and
`GreedyCover` does not — via criterion (a), (b), or both.

| Outcome | Criterion |
|---|---|
| **CONFIRMED** | **≥ 12 of 32** recovered beyond `GreedyCover`'s own baseline on these pairs. Report the (a)-vs-(b) split under every branch — it changes what the finding means, not just how much. |
| **NOT RECOVERED** | **≤ 4 of 32** recovered beyond baseline. Informative, not a failure: it would mean D010's aggregate win comes from elsewhere, and this specific 32-pair gap is exactly as open as D008 (corrected) left it. |
| **PARTIAL / MIXED** | Between 4 and 12 — report the exact count and per-pair detail rather than forcing a binary call. |

## Required steps

**S1 — Load the fixed inputs.** D008's 32-pair list, split-half robust
(`results/D011/premise_check.json`, superseding the naive 33 in
`results/D008/identifiability_frontier.json`), `GreedyCover`'s own `k=8`
chain (`results/D008/selection.json`), `JointGreedy`'s `k=8` chain
(`results/D010/selection.json`).

**S2 — Criterion (a): does any single chosen query resolve the pair on
D008's own scale?** For each of the 32 pairs, per chain, check whether
`max` over the chain's 8 queries of **2-way test accuracy** (D008's own
computation — `d008_lib.summed` / `two_way_correct`, same classifier,
split, and `T2 = 0.75` threshold as the original flag) clears 0.75.
**Report both naive (max over 8) and split-half (per F3 below) —
taking a max over 8 candidates carries a smaller version of Part 0's
own winner's-curse risk; measure it rather than assume it's negligible.**

**S3 — Criterion (b): does the chosen *set* resolve the pair jointly,
where no member does alone?** For each of the 32 pairs, per chain,
compute the **set's own 2-way test accuracy** (same classifier/split/
threshold as S2, applied to the whole chosen `k=8` set rather than one
query at a time) and check whether it clears 0.75 while every
individual query in that same chain fails S2. This keeps (a) and (b) on
one directly comparable scale — **do not introduce a separate
percentile-based threshold on the raw joint statistic as the primary
criterion** (it fixes its own answer's size by construction, per
D008/Call 3's own finding). Report the raw joint-statistic view (against
a `k=8` self-pair null, D010's pilot machinery) as a **labelled
secondary**, not the deciding one.

**S4 — Baseline: run both criteria against `GreedyCover`'s own chain
too**, on the same 32 pairs. There is no longer a specific prior for
what (a) should show here — the pairs were flagged by a per-pair
build→test gap in the tensor's own estimate, not by anything about
`GreedyCover`'s chain — so this is a genuine empirical baseline, not a
sanity check with a known expected answer. (b) is equally open: does
`GreedyCover`'s chosen set resolve any of these pairs jointly, or is
there truly no joint signal in its 8 queries for them? This is the
correct baseline for interpreting whatever `JointGreedy` scores in
S2/S3.

**S5 — Report the full per-pair breakdown**: resolved under (a) only,
(b) only, both, or neither — for both chains — plus the aggregate
counts the outcome table needs.

**S6 — Write `## R`.**
