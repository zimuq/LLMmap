## D — The question

> **Of the 33 pairs D008 flagged — no query in `GreedyCover`'s selected
> chain separates them well, but a near-perfect query exists elsewhere
> in the 259-query pool — does `JointGreedy`'s already-selected `k=8`
> chain (D010) resolve any of them, and via which mechanism: (a) one of
> its 8 chosen queries happens to be individually excellent for that
> pair (the same per-query criterion D008 used), or (b) the chosen set
> resolves it *jointly*, via the concatenated statistic, even though no
> single member does?**

Both are worth distinguishing. (a) would mean `JointGreedy` recovered
these pairs by coincidence — its different objective happened to value
the same individually-strong queries `GreedyCover`'s shared budget
couldn't afford. (b) would mean the recovery is *because* of the
mechanism D010 was built to test — set-level interaction succeeding
where per-query MAX (I4) structurally cannot look. Reporting only an
aggregate "resolved / not resolved" count would blur this distinction,
which is the actual point of running this at all.

### Why this exists now

D008 and D010 are two separate, already-closed findings that have never
been directly cross-referenced. Everything needed is already
computed — no new generation, no new training, no GPU. This is the
cheapest possible way to connect them before deciding anything about
Phase 3's future scope.

### What's already decided and does not block this D

- **No new artifacts.** `S_energy` (D007), the 33-pair list and
  `GreedyCover`'s chain (D008), `JointGreedy`'s chain and its statistic
  implementation (D010) are all reused verbatim (I6). This D reads,
  it does not regenerate or retrain.
- **Stays at the tensor/statistic level, not the trained classifier.**
  D008's original 33-pair finding was itself a tensor-level diagnostic
  (`S_energy` against a threshold), not a trained-classifier result —
  this D answers the same kind of question at the same level, for
  direct comparability. Whether a recovered pair also shows up correctly
  classified in D009/D010's *trained* per-condition results is a
  natural follow-up, not required here.

## What counts as an answer

| Outcome | Criterion |
|---|---|
| **CONFIRMED (meaningful recovery)** | `JointGreedy`'s chain resolves a non-trivial share of the 33 pairs (via (a), (b), or both) that `GreedyCover`'s own chain does not. Report the (a)-vs-(b) split explicitly — it changes what the finding means, not just how much. |
| **NOT RECOVERED** | `JointGreedy`'s chain does no better than `GreedyCover`'s on these specific 33 pairs, under both criteria. Informative, not a failure: it would mean D010's aggregate win comes from elsewhere, and the 33-pair gap is exactly as open as D008 left it. |
| **PARTIAL / MIXED** | A small or ambiguous number recovered — report the exact count and per-pair detail rather than forcing a binary call. |

## Required steps

**S1 — Load the fixed inputs.** D008's 33-pair list
(`results/D008/identifiability_frontier.json`), `GreedyCover`'s own
`k=8` chain (`results/D008/selection.json`), `JointGreedy`'s `k=8` chain
(`results/D010/selection.json`), and the frozen `S_energy` tensor (D007).

**S2 — Criterion (a): per-query overlap.** For each of the 33 pairs,
check whether `max` over `JointGreedy`'s 8 chosen queries of
`S_energy[q][pair]` clears the same threshold `θ` D008/S7 used to
originally flag these pairs. Reuse D008's `θ` unchanged — do not
re-derive a new one.

**S3 — Criterion (b): joint resolution.** For each of the 33 pairs,
compute the joint statistic (D010's own method, `LLMmap/joint_statistic.py`)
restricted to `JointGreedy`'s actual chosen 8-query set, and check
whether it clears an analogous threshold. **Call 1 (flagged for
design-side review):** how to set this threshold — the joint
statistic's scale differs from the per-query one, so D008's raw `θ`
does not transfer directly. Propose a percentile-based threshold
relative to the joint statistic's own distribution (matching how D008's
own `θ` was chosen — a percentile, not an arbitrary absolute cutoff,
per D008/Call 3), or another stated method — do not silently reuse the
raw number.

**S4 — Baseline: run both criteria against `GreedyCover`'s own chain
too**, on the same 33 pairs. (a) should mostly fail — that is exactly
why these pairs were flagged in D008 — confirm it does, as a sanity
check on this D's own methodology. (b) is genuinely open: does
`GreedyCover`'s chosen set, evaluated *jointly* even though it was never
selected for that, accidentally resolve any of these pairs, or is there
truly no joint signal in its 8 queries for them? This is the correct
baseline for interpreting whatever `JointGreedy` scores in S2/S3.

**S5 — Report the full per-pair breakdown**: resolved under (a) only,
(b) only, both, or neither — for both chains — plus the aggregate
counts the outcome table needs.

**S6 — Write `## R`.**

### P1

**Status: PROPOSED — awaiting review.** Full plan:

D011 is the project's smallest D and this P is short on everything except one
thing: **two problems with the premise it inherits**, both originating in text I
wrote in D008's `## R`. Neither kills the D; one makes it sharper.

**Part 0 — the premise, checked.** D008/R10 said *"33 of the 37 have an oracle
≥ 0.95 — some query in the pool separates them nearly perfectly and selection
missed it."* D008's own artifact carries a caveat its `## R` narration dropped:
that oracle is `max over 259 queries of TEST accuracy`, **selected on the
evaluation split**, over 50 traces — the winner's curse D007/F2 already corrected
for once here. Measured with the same fix (select on half the test configs, score
on the other half):

| criterion | ≥0.95 | mean |
|---|---|---|
| naive oracle, all 25 configs *(D008's number)* | **33 / 37** | 0.977 |
| honest — pick `q*` on half A, score on half B | **18 / 37** | 0.908 |
| **split-half robust — clears the bar on *both* halves** | **32 / 37** | 0.970 |
| median query, no selection | — | 0.811 |

Mean shrinkage naive → honest: **+0.069**.

**Both directions, stated plainly.** The concern was right in mechanism: D008's
per-pair oracle figures are **optimistic by ~7 accuracy points**. But the
qualitative claim **survives** — requiring a query to clear 0.95 on two
*independent* halves, which noise cannot fake twice, still passes **32 of 37**.
The 18/37 column is itself downward-biased (12 configs = 24 traces, so 0.95 needs
23/24). The truth is bracketed by 18 and 32, and 32 is the more informative bound
because it demands consistency rather than one lucky split. **Proposal: proceed,
and restate the headline as "32 of 37, split-half robust", retiring the bare 33.**

**F1 — the flagged pairs have nothing to do with `GreedyCover`'s chain.** D011's
`## D` describes them as pairs *"no query in `GreedyCover`'s selected chain
separates well"*. That is not what D008 computed —
`experiments/d008_frontier.py:95` is `qstar = S.argmax(axis=0)`, the argmax over
**all 259 queries** per pair; the chain never enters that script. T2 means *the
build tensor's top-ranked query for this pair scores <75% on test while another
query does much better* — a per-pair selection error, not a shared-budget effect.
**Consequence:** S4's stated sanity check (*"(a) should mostly fail — that is
exactly why these pairs were flagged"*) is not valid reasoning; nothing about T2
constrains what either chain does here. S4 remains the right baseline, for a
different reason. Logged to `TACC_NOTES` (`## D` is design-side owned); not
blocking.

**F2 — S2's threshold is on the wrong scale.** D008/S7 has three θ's: T1 = 0.1303
(`S_energy`), **T2 = 0.75 (2-way test accuracy)**, T3 = 0.8761 (`S_energy`). These
37 pairs are **T2's**, so "D008's θ" for them is an accuracy threshold — there is
no `S_energy` θ that flagged them, and applying T1's or T3's would silently change
the population. **Proposal: run (a) on T2's accuracy scale**, with the `S_energy`
view reported as a labelled secondary.

**Call 1 — proposal: don't invent a joint-statistic threshold as primary.** Put
(a), (b) and the original flag on one scale: **(a)** = max over the chain's 8
queries of single-query 2-way test accuracy ≥ 0.75; **(b)** = the *set's* 2-way
accuracy ≥ 0.75 while (a) fails — the 8 together resolving what none resolves
alone — via D008's own proxy (`d008_lib.summed` + `two_way_correct`), same
classifier, same split, same threshold as the flag. Mechanism view kept as
secondary: the joint statistic against a **`k=8` self-pair null** (D008/Call 3's
T1 construction; machinery exists from D010's pilot). A percentile of the
statistic's own distribution is the one option I'd argue against — as D008/Call 3
already found, it fixes its answer's size by construction.

**F3 — don't repeat the mistake Part 0 just diagnosed.** (a) takes a max over 8
queries, so it carries a small winner's curse of its own; the chains are clean
(both selected on `S_build`), but that max is not. Report (a) naive **and**
split-half. With 8 candidates rather than 259 the inflation should be small —
measuring it costs nothing, and this D is precisely a lesson in not assuming that.

**F4 — "non-trivial share" needs a number before the count exists.**
Pre-registering: **≥12 of 37** recovered beyond `GreedyCover`'s baseline →
CONFIRMED; **≤4 beyond** → NOT RECOVERED; in between → PARTIAL/MIXED. The (a)/(b)
split is reported under every branch, since a recovery that is entirely (a) means
something different from one that is even partly (b).

**Cost:** ~2 minutes, one `gh` job. **New file only:**
`experiments/d011_recovery.py`; everything else imported from `d008_lib`,
`LLMmap/joint_statistic.py`, `d007_lib`.

**Verification that licenses the rest:** the naive oracle recomputation had to
reproduce D008's **33/37** exactly before any new number could be trusted. It does.
