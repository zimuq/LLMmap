## D — The question

> **Of the 33 pairs D008 flagged — no query in `GreedyCover`'s selected
> chain separates them well, but a near-perfect query exists elsewhere
> in the 259-query pool — does `JointGreedy`'s already-selected `k=8`
> chain (D010) resolve any of them, and via which mechanism: (a) one of
> its 8 chosen queries happens to be individually excellent for that
> pair (the same per-query criterion D008 used), or (b) the chosen set
> resolves it *jointly*, via the concatenated statistic, even though no
> single member does?**

Both are worth distinguishing. (a) would mean `JointGreedy` recovered
these pairs by coincidence — its different objective happened to value
the same individually-strong queries `GreedyCover`'s shared budget
couldn't afford. (b) would mean the recovery is *because* of the
mechanism D010 was built to test — set-level interaction succeeding
where per-query MAX (I4) structurally cannot look. Reporting only an
aggregate "resolved / not resolved" count would blur this distinction,
which is the actual point of running this at all.

### Why this exists now

D008 and D010 are two separate, already-closed findings that have never
been directly cross-referenced. Everything needed is already
computed — no new generation, no new training, no GPU. This is the
cheapest possible way to connect them before deciding anything about
Phase 3's future scope.

### What's already decided and does not block this D

- **No new artifacts.** `S_energy` (D007), the 33-pair list and
  `GreedyCover`'s chain (D008), `JointGreedy`'s chain and its statistic
  implementation (D010) are all reused verbatim (I6). This D reads,
  it does not regenerate or retrain.
- **Stays at the tensor/statistic level, not the trained classifier.**
  D008's original 33-pair finding was itself a tensor-level diagnostic
  (`S_energy` against a threshold), not a trained-classifier result —
  this D answers the same kind of question at the same level, for
  direct comparability. Whether a recovered pair also shows up correctly
  classified in D009/D010's *trained* per-condition results is a
  natural follow-up, not required here.

## What counts as an answer

| Outcome | Criterion |
|---|---|
| **CONFIRMED (meaningful recovery)** | `JointGreedy`'s chain resolves a non-trivial share of the 33 pairs (via (a), (b), or both) that `GreedyCover`'s own chain does not. Report the (a)-vs-(b) split explicitly — it changes what the finding means, not just how much. |
| **NOT RECOVERED** | `JointGreedy`'s chain does no better than `GreedyCover`'s on these specific 33 pairs, under both criteria. Informative, not a failure: it would mean D010's aggregate win comes from elsewhere, and the 33-pair gap is exactly as open as D008 left it. |
| **PARTIAL / MIXED** | A small or ambiguous number recovered — report the exact count and per-pair detail rather than forcing a binary call. |

## Required steps

**S1 — Load the fixed inputs.** D008's 33-pair list
(`results/D008/identifiability_frontier.json`), `GreedyCover`'s own
`k=8` chain (`results/D008/selection.json`), `JointGreedy`'s `k=8` chain
(`results/D010/selection.json`), and the frozen `S_energy` tensor (D007).

**S2 — Criterion (a): per-query overlap.** For each of the 33 pairs,
check whether `max` over `JointGreedy`'s 8 chosen queries of
`S_energy[q][pair]` clears the same threshold `θ` D008/S7 used to
originally flag these pairs. Reuse D008's `θ` unchanged — do not
re-derive a new one.

**S3 — Criterion (b): joint resolution.** For each of the 33 pairs,
compute the joint statistic (D010's own method, `LLMmap/joint_statistic.py`)
restricted to `JointGreedy`'s actual chosen 8-query set, and check
whether it clears an analogous threshold. **Call 1 (flagged for
design-side review):** how to set this threshold — the joint
statistic's scale differs from the per-query one, so D008's raw `θ`
does not transfer directly. Propose a percentile-based threshold
relative to the joint statistic's own distribution (matching how D008's
own `θ` was chosen — a percentile, not an arbitrary absolute cutoff,
per D008/Call 3), or another stated method — do not silently reuse the
raw number.

**S4 — Baseline: run both criteria against `GreedyCover`'s own chain
too**, on the same 33 pairs. (a) should mostly fail — that is exactly
why these pairs were flagged in D008 — confirm it does, as a sanity
check on this D's own methodology. (b) is genuinely open: does
`GreedyCover`'s chosen set, evaluated *jointly* even though it was never
selected for that, accidentally resolve any of these pairs, or is there
truly no joint signal in its 8 queries for them? This is the correct
baseline for interpreting whatever `JointGreedy` scores in S2/S3.

**S5 — Report the full per-pair breakdown**: resolved under (a) only,
(b) only, both, or neither — for both chains — plus the aggregate
counts the outcome table needs.

**S6 — Write `## R`.**
